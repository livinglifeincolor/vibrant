## 정규 문법과 촘스키 계층 구조

### Regular Grammar (정규 문법)의 정의

**Regular Grammar**(정규 문법)는 정규 언어(Regular Language)를 생성하는 문법으로, 촘스키 계층 구조에서 가장 제한적인 형식을 가집니다. 일반적으로 **Type-3 grammar**라고도 불립니다.

#### 1. 생산 규칙의 형식

정규 문법은 모든 생산 규칙이 다음 두 가지 형태 중 하나를 따라야 합니다 (A, B는 비단말 기호, a는 단말 기호).

- **우선형 정규 문법 (Right-Linear Grammar):**
  - $A \rightarrow aB$
  - $A \rightarrow a$ (또는 $A \rightarrow \epsilon$)
- **좌선형 정규 문법 (Left-Linear Grammar):**
  - $A \rightarrow Ba$
  - $A \rightarrow a$ (또는 $A \rightarrow \epsilon$)

하나의 정규 문법 내에서는 우선형과 좌선형 규칙을 혼합해서 사용할 수 없으며, 반드시 한 가지 형태만을 유지해야 합니다.

#### 2. 정규 표현식과의 관계

모든 정규 표현식(Regular Expression, RE) $r$에 대하여, $L(r) = L(g)$를 만족하는 정규 문법 $g$가 반드시 존재합니다. 즉, 정규 문법은 정규 표현식 및 유한 오토마타(DFA/NFA)와 표현 능력이 동일합니다.

### Chomsky Hierarchy (촘스키 계층 구조)

컴퓨터 과학의 거장 노엄 촘스키는 언어의 복잡도에 따라 문법을 네 가지 단계로 분류했습니다. 계층이 높아질수록(숫자가 작아질수록) 문법의 제약은 줄어들고 표현할 수 있는 언어의 범위는 넓어집니다.

| 계층 (Type) | 문법 명칭                     | 허용되는 오토마타              | 설명                                                 |
| :---------- | :---------------------------- | :----------------------------- | :--------------------------------------------------- |
| **Type 3**  | **Regular Grammar**           | Finite Automaton (DFA, NFA)    | 가장 제약이 많음. 토큰 분석 등에 사용.               |
| **Type 2**  | **Context-Free Grammar**      | Pushdown Automaton (PDA)       | 프로그래밍 언어의 구문 분석(Parsing)에 주로 사용.    |
| **Type 1**  | **Context-Sensitive Grammar** | Linear Bounded Automaton (LBA) | 생성 규칙의 왼쪽 길이가 오른쪽보다 작거나 같아야 함. |
| **Type 0**  | **Unrestricted Grammar**      | Turing Machine                 | 아무런 제약이 없으며, 모든 계산 가능한 언어를 포함.  |

#### 계층 간 포함 관계

이 구조는 **포함 관계**를 가집니다.
$$Type 3 \subset Type 2 \subset Type 1 \subset Type 0$$
즉, 모든 정규 문법은 문맥 자유 문법(CFG)에 해당하지만, 역은 성립하지 않습니다. 예를 들어, 괄호의 짝을 맞추는 언어($a^n b^n$)는 문맥 자유 언어이지만 정규 문법으로는 표현할 수 없습니다.

## CYK Algorithm Pseudocode 설명

```python
# s: n개의 토큰으로 구성된 입력 문자열 (a1, a2, ..., an)
# r: 문법 G에 존재하는 비단말 심볼(Non-terminal)의 개수
# R1: 시작 심볼 (Start symbol)

# 1. 테이블 초기화
# P[n, n, r] 3차원 배열을 모두 false로 설정
# P[i, j, k]의 의미: i부터 j까지의 부분 문자열이 k번째 비단말 심볼로 유도 가능한가?
initialize all entries in P[N, N, r] = false

# 2. Base Case: 길이 1인 부분 문자열 처리 (단말 노드)
# 입력 문자열의 각 토큰(ai)에 대해, 해당 토큰을 생성하는 생성 규칙(Rk -> ai)을 찾음
for each i = 0 to n-1:
    for each unit production Rk -> ai:
        P[i, i+1, k] = true  # i번째 위치의 토큰이 Rk로 파싱됨을 기록

# 3. Inductive Step: 길이가 2 이상인 부분 문자열 처리 (동적 계획법)
# i: 검사할 부분 문자열의 길이 (2부터 n까지 확장)
for i = 2 to n:
    # j: 부분 문자열의 시작 인덱스
    for j = 0 to n-i:
        # k: 부분 문자열을 두 부분으로 나누는 분할 지점 (Partitioning)
        for k = 1 to i-1:
            # 모든 생성 규칙 RA -> RB RC에 대하여 검사
            for each production rule RA -> RB RC:
                # 왼쪽 부분(j ~ j+k)이 RB로 파싱되고,
                # 오른쪽 부분(j+k ~ j+i)이 RC로 파싱되는지 확인
                if P[j, j+k, B] and P[j+k, j+i, C]:
                    P[j, j+i, A] = true  # 두 부분이 합쳐져 RA로 파싱 가능함

# 4. 최종 결과 확인
# 전체 문자열(0부터 n까지)이 시작 심볼(R1)로 파싱되는지 확인
if P[0, n, R1] is true:
    return "s is in L(G)"  # 문법에 맞는 문장임
else:
    return "s is not in L(G)" # 문법에 맞지 않는 문장임
```

### 핵심 메커니즘 요약

- **Chomsky Normal Form (CNF):** CYK 알고리즘은 문법이 $A \rightarrow BC$ 또는 $A \rightarrow a$ 형태인 **촘스키 정규형**일 때 가장 효율적으로 동작합니다.
- **복잡도:** \* **시간 복잡도:** $O(n^3 \cdot r)$ — 입력 길이($n$)의 세제곱에 비례하며, 비단말 심볼 개수($r$)에 영향을 받습니다.
  - **공간 복잡도:** $O(n^2 \cdot r)$ — 결과를 저장하기 위한 3차원 테이블이 필요합니다.
- **작동 방식:** 작은 단위(토큰 1개)에서 시작하여, 이미 계산된 하위 문제의 결과(`P[j, j+k, B]`와 `P[j+k, j+i, C]`)를 조합해 더 큰 단위의 문법 구조를 완성해 나가는 방식입니다.

## 정규 문법과 문맥 자유 문법의 이론적 한계점

### 정규 문법(Regular Grammars)의 한계

정규 문법은 스캐너(Scanner)가 토큰을 식별하는 데 사용되지만, 프로그램의 전체 구조를 정의하기에는 부족합니다.

- **중첩 구조(Nested Constructs) 표현 불가**: 정규 문법은 괄호가 중첩되거나 제어문이 중첩되는 구조를 인식할 수 없습니다.
- **자기 호출의 부재**: 정규 문법은 유한 오토마타(Finite Automata)를 기반으로 하는데, 이는 '기억 장치(메모리)'가 없어서 상태의 개수가 유한합니다.
- **대표적인 예시 ($L=\{a^{n}b^{n}|n\ge0\}$)**:
  - $a$가 나온 횟수만큼 동일한 횟수의 $b$가 나와야 하는 언어는 정규 언어가 아닙니다.
  - 반면, 문맥 자유 문법은 $S\rightarrow\epsilon|aSb$와 같은 재귀적 규칙을 통해 이를 쉽게 표현할 수 있습니다.
- **결론**: 정규 문법은 중첩되지 않는 단순 토큰 정의에는 강력하지만, "숫자를 세는 것(Counting)"과 같은 연산이 필요한 구조는 처리할 수 없습니다.

### 문맥 자유 문법(Context-Free Grammars)의 한계

대부분의 프로그래밍 언어 구조는 CFG로 표현 가능하지만, 일부 중요한 특징들은 CFG의 범위를 벗어납니다. 이러한 요소들은 구문 분석(Parsing) 단계가 아닌 **의미 분석(Semantic Analysis)** 단계에서 처리되어야 합니다.

- **변수 선언 후 사용 ($L=\{wcw|w \in (a|b)^{*}\}$)**:
  - 앞에서 선언된 변수명($w$)이 나중에 사용되는 변수명($w$)과 동일해야 한다는 규칙은 CFG로 표현할 수 없습니다. 이는 문맥 민감(Context-sensitive)한 특성이기 때문입니다.
- **함수 호출 시 인자 개수 일치 ($L=\{a^{n}b^{m}c^{n}d^{m}|n\ge1,m\ge1\}$)**:
  - 두 개의 서로 다른 함수가 각각 $n$개와 $m$개의 매개변수를 가질 때, 호출 시에도 각각 정확히 $n$개, $m$개의 인자를 전달했는지 체크하는 구조는 CFG의 표현 범위를 초과합니다.
- **기술적 시사점**:
  - CFG가 포착하지 못하는 언어적 특징들은 컴파일러의 다음 단계인 **의미 분석(Semantic Analysis)** 단계에서 심볼 테이블(Symbol Table) 등을 활용해 별도로 체크해야 합니다.

### 요약 및 계층적 관점

| 문법 타입          | 주요 용도              | 한계점                                         |
| :----------------- | :--------------------- | :--------------------------------------------- |
| **정규 문법**      | 어휘 분석 (Tokenizing) | 중첩 구조 및 카운팅 불가                       |
| **문맥 자유 문법** | 구문 분석 (Parsing)    | 식별자 일치 여부 등 문맥 의존적 정보 확인 불가 |

이러한 한계 때문에 컴파일러는 각 단계마다 적절한 문법 체계를 선택하여 사용하며, CFG로 해결 안 되는 부분은 의미 분석 단계의 로직으로 보완하게 됩니다.

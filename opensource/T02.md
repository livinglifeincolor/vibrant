## 주요 내용 및 키워드

### 1. Git의 핵심 아키텍처 및 데이터 모델

- **Immutable Object Model**: Git은 모든 변경 사항을 '불변의 스냅샷'으로 관리합니다.
- **Content-Addressable Storage**: 파일 시스템이 아닌 키-값 기반의 객체 저장소로 동작하며, SHA-1 해시값이 각 객체의 고유 주소(Key) 역할을 합니다.
- **4대 주요 객체**:
  - **Blob**: 파일의 원본 데이터를 저장합니다.
  - **Tree**: 디렉토리 구조를 나타내며 Blob이나 다른 Tree를 가리킵니다.
  - **Commit**: 루트 Tree의 해시, 메타데이터(저자, 날짜 등), 부모 커밋 포인터를 포함합니다.
  - **Tag**: 특정 커밋에 대한 영구적인 참조입니다.
- **DAG (Directed Acyclic Graph)**: Git의 히스토리는 커밋을 노드로, 부모 포인터를 간선으로 하는 방향성 비순환 그래프 구조를 가집니다.

### 2. Git의 논리적 영역과 워크플로우

- **Working Directory**: 실제 디스크에서 파일을 수정하는 물리적 공간입니다.
- **Index (Staging Area)**: 다음 커밋을 위해 준비된 변경 사항을 유지하는 바이너리 파일 기반의 완충 지대입니다.
- **Local Repository**: 커밋된 데이터가 SHA-1 해시 기반 객체로 영구 저장되는 데이터베이스 공간입니다.
- **HEAD**: 현재 체크아웃된 브랜치나 특정 커밋을 가리키는 이동 가능한 포인터입니다.

### 3. 브랜치 전략 및 병합 알고리즘

- **Lightweight Branch**: 브랜치는 단순한 포인터 파일에 불과하며, 생성과 삭제의 시간 복잡도는 $O(1)$입니다.
- **Merge Algorithms**:
  - **Fast-Forward (FF)**: 대상 브랜치가 선조(Ancestor)일 경우 별도의 커밋 생성 없이 포인터만 이동합니다.
  - **3-way Merge**: 공통 조상을 기준으로 두 브랜치의 변경 사항을 병합하며 새로운 커밋 객체를 생성합니다.
- **Rebase**: 브랜치의 기반(Base)을 변경하여 복잡한 DAG를 선형적(Linear)인 구조로 재배치하는 히스토리 재작성 기술입니다. (공개된 커밋에는 사용을 금지하는 'The Rule of Rebase' 준수 필요)

### 4. 트랜잭션 복구 및 최적화 기술

- **Reset**: HEAD 포인터를 이전 커밋으로 이동시켜 히스토리를 절단합니다. 옵션에 따라 Index와 Working Directory의 동기화 수준이 결정됩니다. (`--soft`, `--mixed`, `--hard`)
- **Revert**: 기존 커밋의 변경 내용을 반전시킨 새로운 커밋을 생성합니다. 히스토리를 유지해야 하는 공용 브랜치에 적합한 안전한 롤백 방식입니다.
- **Squash**: 여러 개의 작은 커밋을 하나의 의미 있는 단위로 통합하여 히스토리 가독성을 높입니다.

### 5. 핵심 키워드 요약

| :-------------- | :--------------------------------------------------------------------- |
| **데이터 구조** | Immutable Snapshot, SHA-1 Hash, DAG, Content-Addressable               |
| **객체 타입**   | Blob, Tree, Commit, Tag                                                |

## 깃의 세 가지 논리적 영역

### 1. 개요

Git은 모든 변경 사항을 **불변의 스냅샷(Immutable Snapshot)**으로 관리하며, 이를 효율적으로 처리하기 위해 워킹 디렉토리, 인덱스, 로컬 저장소라는 세 가지 논리적 계층을 둡니다.

### 2. 세부 영역 분석

#### ① Working Directory (Untracked/Modified Area)

개발자가 실제로 코드를 작성하고 파일을 수정하는 물리적인 작업 공간입니다.

- **물리적 위치:** 프로젝트 폴더 내에서 `.git` 디렉토리를 제외한 실제 파일들입니다.
- **파일 상태:** \* **Modified:** 기존에 추적되던 파일이 수정됨
  - **Untracked:** 새로 생성되어 아직 Git이 관리하지 않음
  - **Unmodified:** 마지막 커밋 이후 변경 사항이 없음

#### ② Index / Staging Area (Committed Area)

다음 커밋에 포함될 파일들의 스냅샷을 임시로 기록하는 버퍼 영역입니다.

- **물리적 위치:** `.git/index` 파일로 존재하며, Git에 의해 바이너리 형태로 관리됩니다.
- **역할:** 워킹 디렉토리에서 수정한 내용 중 '버전'으로 기록하고 싶은 것만 선별(Stage)하여 담아두는 준비 공간입니다. Git은 워킹 디렉토리가 아닌 이 **Index 영역의 콘텐츠를 기반으로 커밋을 생성**합니다.

#### ③ Local Repository (Committed Area)

최종적으로 확정된 변경 사항이 영구히 저장되는 객체 데이터베이스입니다.

- **물리적 위치:** 프로젝트 내 숨겨진 `.git` 폴더 내부에 위치합니다.
- **특징:** Staging Area에 있던 스냅샷이 **SHA-1 해시 기반의 불변 객체** 시리즈로 저장됩니다. 한 번 기록된 이력은 데이터베이스에 영구적으로 보존되어 변경이 불가능한 '불변의 역사'를 형성합니다.

### 3. 데이터의 흐름과 상태 전환

1.  **Checkout:** 저장소(`Repository`)에 있는 특정 버전을 내려받아 워킹 디렉토리(`Working Directory`)를 업데이트합니다.
2.  **Stage Fixes (`git add`):** 워킹 디렉토리에서 수정한 내용을 인덱스(`Staging Area`)로 올려 기록 대기 상태로 만듭니다.
3.  **Commit (`git commit`):** 인덱스에 있는 스냅샷을 로컬 저장소(`Repository`)에 영구적으로 기록합니다. 이때 **HEAD** 포인터가 최신 커밋을 가리키도록 업데이트됩니다.

이러한 단계적 구조 덕분에 개발자는 수많은 변경 사항 중 원하는 부분만 골라서 커밋하거나, 작업 중인 내용을 안전하게 나누어 관리할 수 있습니다.

## Content-Addressable Storage

Git에서 사용하는 **콘텐츠 주소 지정 가능 저장소(Content-Addressable Storage)**는 데이터의 파일 이름이나 위치가 아닌, 데이터의 **내용(Content)** 자체를 식별자로 사용하여 저장하고 관리하는 메커니즘입니다.

### 1. 핵심 메커니즘: Hashing & Key-Value Store

Git은 내부적으로 단순한 파일 시스템이 아니라, 고도의 **Key-Value 객체 저장소**처럼 동작합니다.

- **해싱 (Hashing):** 모든 데이터(파일 내용, 디렉토리 구조, 커밋 메시지 등)는 **SHA-1** 알고리즘을 통해 160비트(40자 16진수)의 고유한 해시값으로 변환됩니다.
- **Key-Value 구조**
  - **Key:** 생성된 SHA-1 해시값이 데이터의 주소(Address)가 됩니다.
  - **Value:** 실제 데이터의 내용(zlib로 압축된 상태)이 저장됩니다.
- **불변성 (Immutability):** 데이터의 내용이 1비트라도 바뀌면 해시값이 완전히 달라집니다. 따라서 한 번 저장된 객체는 수정되지 않으며, 변경 사항은 항상 새로운 객체로 생성됩니다.

### 2. 저장 효율성: 중복 제거 (Deduplication)

이 방식의 가장 큰 장점 중 하나는 저장 공간을 획기적으로 아낄 수 있다는 점입니다.

- **내용 기반 식별:** 파일 이름이 달라도 내용이 완전히 일치한다면, Git은 이를 동일한 하나의 **Blob 객체**로 취급하여 단 한 번만 저장합니다.
- **포인터 활용:** 서로 다른 폴더에 있거나 버전이 바뀌어도 내용이 같다면, Git의 Tree 객체는 단순히 기존에 생성된 동일한 해시값(Key)을 가리키기만 합니다.

### 3. 데이터 무결성 (Integrity)

- **식별자가 곧 검증 키:** 데이터의 주소(해시값)가 내용에서 산출되므로, 데이터를 불러온 뒤 다시 해싱해보면 파일이 손상되었는지 즉시 확인할 수 있습니다.
- **보안:** 전송 중 데이터가 위변조될 경우 해시값이 일치하지 않게 되므로, 데이터 무결성이 완벽하게 보장됩니다.

### 4. 물리적 저장 방식

실제 로컬 저장소의 `.git/objects` 디렉토리를 확인하면 이 메커니즘을 시각적으로 이해할 수 있습니다.

- **디렉토리 분할:** 40자의 해시값 중 앞의 **2글자**를 디렉토리 이름으로 사용하고, 나머지 **38글자**를 파일 이름으로 사용합니다. (예: `a9/0d190...`)
- **접근 방법:** `git cat-file -p <hash>` 명령어를 사용하면 해당 해시 주소에 저장된 실제 내용을 역으로 조회할 수 있습니다.

### 5. 요약

| 구분          | 특징                                                       |
| :------------ | :--------------------------------------------------------- |
| **주소 결정** | 파일 경로가 아닌 **파일 내용**에 의해 결정됨               |
| **알고리즘**  | **SHA-1** (40자 Hex string)                                |
| **장점**      | 자동 중복 제거, 데이터 무결성 보장, 빠른 검색 속도         |
| **성격**      | 기술적으로 Git은 파일 시스템보다 **데이터베이스**에 가까움 |

## Fundamental Objects

Git은 파일 시스템이 아닌 콘텐츠 주소 지정이 가능한 **Key-Value Object Store**로 작동하며, 모든 객체는 zlib으로 압축된 후 SHA-1 해시(160-bit)를 통해 고유한 키값을 부여받습니다.

### 1. Blob (Binary Large Object)

- **역할**: 파일의 실제 **데이터(Raw content)** 자체를 저장하는 단위입니다.
- **특징**: 파일 이름이나 권한 같은 메타데이터는 포함하지 않으며 오직 내용만 저장합니다.
- **효율성**: 서로 다른 경로에 있더라도 파일 내용이 동일하다면 동일한 SHA-1 해시를 공유하므로, 내부적으로 **중복 제거(Deduplication)**가 자동으로 수행됩니다.

### 2. Tree

- **역할**: 파일 시스템의 **디렉토리(Directory) 구조**를 표현합니다.
- **구성**: 해당 디렉토리에 포함된 **Blob**의 포인터나 하위 **Tree**의 포인터, 그리고 해당 파일/폴더의 이름과 권한 정보를 매핑하여 저장합니다.
- **스냅샷 메커니즘**: 특정 파일(Blob)이 수정되어 해시가 변경되면, 해당 Blob을 포함하는 Tree의 해시가 변경되고 이는 다시 상위 부모 Tree들의 해시 변경으로 이어지는 연쇄 효과(Cascade)를 통해 전체 프로젝트의 스냅샷을 생성합니다.

### 3. Commit

- **역할**: 특정 시점의 전체 프로젝트 상태를 나타내는 **스냅샷(Root Tree)**과 관련 메타데이터를 저장합니다.
- **데이터 필드**:
  - **Root Tree Pointer**: 커밋 시점의 최상위 Tree 객체 해시값.
  - **Metadata**: 저자(Author), 커미터(Committer), 날짜, 커밋 메시지.
  - **Parent Pointer**: 이전 커밋 객체의 해시값을 가리키며, 이를 통해 Git의 이력은 **방향성 비순환 그래프(DAG)** 구조를 형성합니다.

### 4. Tag

- **역할**: 특정 커밋에 부여하는 **영구적인 참조(Reference)**입니다.
- **특징**: 브랜치와 달리 포인터가 이동하지 않는 고정된 지점을 의미하며, 주로 소프트웨어 출시 버전(v1.0, v1.1 등)을 관리할 때 사용됩니다. 디지털 서명을 포함하여 보안 검증에 활용될 수도 있습니다.

**기술적 검증 도구 (CLI)**
Git 내부 저장소에서 위 객체들의 내용을 직접 확인하려면 다음 명령어를 사용합니다:

- 객체 내용 출력: `git cat-file -p <hash>`
- 객체 타입 확인: `git cat-file -t <hash>`

## 히스토리 구조와 포인터 메커니즘

### 1. Directed Acyclic Graph (DAG)

Git의 히스토리는 기본적으로 **방향성 비순환 그래프(DAG)** 구조를 가집니다.

- **그래프 토폴로지(Graph Topology):** 커밋 객체는 그래프의 **노드(Nodes)**가 되고, 이전 커밋을 가리키는 부모 포인터는 **방향성 간선(Directed Edges)**이 됩니다.
- **불변성(Immutability):** 모든 커밋은 콘텐츠와 결합된 고유한 SHA-1 해시값을 가집니다. 내용이 조금이라도 변경되면 새로운 해시를 가진 별개의 커밋 객체가 생성되어 히스토리의 무결성을 보장합니다.
- **그래프 순회(Graph Traversal):** `git log`와 같은 명령은 HEAD 노드에서 시작하여 $DFS/BFS$ 알고리즘을 통해 그래프를 탐색하고 히스토리를 재구성하여 보여줍니다.

### 2. Branch: 가볍고 이동 가능한 포인터

브랜치는 파일의 복사본이 아니라 특정 커밋을 가리키는 **상징적 참조(Symbolic Reference)**입니다.

- **물리적 실체:** `.git/refs/heads/<브랜치명>` 경로에 위치한 41바이트의 작은 텍스트 파일로, 해당 브랜치가 가리키는 커밋의 SHA-1 해시값을 담고 있습니다.
- **효율성:** 브랜치를 생성하거나 삭제하는 작업은 단순히 파일 하나를 다루는 것과 같으므로 **$O(1)$**의 시간 복잡도를 가집니다.

### 3. HEAD: 현재 상태 표시자

HEAD는 현재 작업 중인 체크아웃 상태를 나타내는 지표입니다.

- **역할:** 활성화된 브랜치나 특정 커밋을 가리키는 포인터(`.git/HEAD`)입니다.
- **컨텍스트 스위칭(Context Switching):** `git switch <브랜치>` 명령을 실행하면 다음과 같은 상태 전이(State Transition)가 일어납니다.
  1.  **HEAD** 포인터를 대상 브랜치로 업데이트합니다.
  2.  대상 커밋의 **Tree** 데이터를 읽어옵니다.
  3.  **Index**와 **Working Directory**를 해당 상태로 갱신합니다.

## Merge Algorithms

### 1. Fast-Forward (FF) Merge

대상 브랜치의 이력이 현재 브랜치의 이력을 포함하고 있는 선형적인 구조일 때 발생하는 병합 방식입니다.

- **메커니즘:** 현재 브랜치(예: `main`)가 대상 브랜치(`feature`)의 직접적인 조상일 경우, Git은 별도의 커밋 객체를 생성하지 않고 브랜치 포인터만 대상 브랜치의 끝으로 이동시킵니다. \* **특징:** 새로운 머지 커밋이 생성되지 않으므로, 전체적인 **Directed Acyclic Graph (DAG)** 경로가 완벽하게 선형적이고 깔끔하게 유지됩니다.

### 2. 3-way Merge

두 브랜치가 공통 조상에서 갈라져 나와 서로 다른 커밋 이력을 쌓았을 때 사용되는 알고리즘입니다.

- **메커니즘:** 다음 세 가지 지점을 비교하여 병합을 수행합니다.
  1.  **Common Ancestor (C2):** 두 브랜치가 갈라지기 전의 공통 지점입니다.
  2.  **Snapshot to Merge Into (C4):** 현재 브랜치(master)의 최신 상태입니다.
  3.  **Snapshot to Merge In (C5):** 병합해 올 대상 브랜치(new-feature)의 최신 상태입니다.
- **Merge Commit (C6):** 3-way 병합의 결과로 두 개의 부모 포인터를 가진 새로운 **Merge Commit**이 생성되며, 이를 통해 분기되었던 이력이 다시 하나로 합쳐집니다.

### 3. 요약 비교

| 구분            | Fast-Forward                   | 3-way Merge           |
| :-------------- | :----------------------------- | :-------------------- |
| **발생 조건**   | 이력이 선형적일 때 (조상 관계) | 이력이 분기되었을 때  |
| **커밋 생성**   | 생성 안 함 (포인터만 이동)     | 새로운 머지 커밋 생성 |
| **그래프 형태** | 일직선 유지                    | 분기 후 합쳐지는 형태 |

## Rebase

Git의 **Rebase**는 분기된 히스토리를 하나의 선형적인 흐름으로 재정렬하는 강력한 도구입니다. 기술적인 관점에서 Rebase의 메커니즘과 전략을 정리해 드립니다.

### 1. Rebase의 정의 및 목적

Rebase는 특정 브랜치의 **기반(Base)**이 되는 커밋을 다른 지점으로 옮기는 작업입니다.

- **히스토리 선형화**: 여러 갈래로 갈라진 DAG(Directed Acyclic Graph) 구조를 하나의 일직선상으로 정렬하여 가독성을 극대화합니다.
- **Merge와의 차이**: Merge는 두 갈래의 끝을 잇는 새로운 'Merge Commit'을 생성하지만, Rebase는 기존 커밋들을 복사하여 대상 브랜치 끝에 이어 붙입니다.

### 2. 동작 메커니즘 (git rebase <base>)

Rebase는 내부적으로 다음의 **State Machine Transition** 과정을 거칩니다:

1.  **차이점 추출**: 현재 브랜치와 대상 브랜치(Base)의 공통 조상을 찾고, 그 이후 발생한 현재 브랜치의 커밋들을 별도의 **임시 패치(Patch)**로 추출합니다.
2.  **브랜치 재설정**: 현재 브랜치의 포인터를 대상 브랜치의 최신 커밋(Tip)으로 이동(Reset)시킵니다.
3.  **패치 적용**: 추출했던 패치들을 대상 브랜치 위에 순차적으로 하나씩 적용합니다.
4.  **객체 재생성**: 이 과정에서 내용이 같더라도 부모 포인터와 타임스탬프가 달라지므로, **새로운 커밋 해시(SHA-1)**를 가진 객체들이 생성됩니다.

### 3. Rebase의 황금률 (The Golden Rule)

> **"이미 공개된(Public) 커밋은 절대 Rebase 하지 마라."**

Rebase는 기존 커밋 해시를 변조하기 때문에, 이미 리모트 저장소에 푸시되어 다른 개발자가 공유 중인 히스토리를 Rebase 하면 심각한 문제를 야기합니다.

- **Inconsistency**: 다른 팀원의 로컬 히스토리와 리모트 히스토리가 완전히 달라져, 이후 `git pull` 시 복잡한 병합 충돌과 중복 커밋이 발생합니다.
- **권장 사례**: 로컬에서 작업 중인 개인 브랜치를 메인 브랜치에 합치기 직전, 히스토리를 깔끔하게 정리할 때만 사용해야 합니다.

### 4. Rebase의 주요 전략 및 옵션

- **Interactive Rebase (`-i`)**: 커밋 순서 변경, 커밋 메시지 수정, 여러 커밋을 하나로 합치기(Squash) 등이 가능한 대화형 모드입니다.
- **Rebase Squash**: "WIP(Work In Progress)"나 "Typo fix" 같은 자잘한 커밋들을 하나의 의미 있는 기능 단위 커밋으로 합쳐서 메인 히스토리에 병합할 때 주로 사용합니다.
- **Conflict Resolution**: Rebase 도중 충돌이 발생하면 수정한 후 `git rebase --continue`를 통해 다음 패치를 적용하거나, `git rebase --abort`로 작업을 취소하고 원래 상태로 돌아갈 수 있습니다.

Rebase를 적절히 활용하면 프로젝트의 히스토리를 마치 처음부터 한 줄로 개발된 것처럼 깨끗하게 유지할 수 있습니다.

## Squash

**Squash**는 여러 개의 커밋을 하나의 의미 있는 커밋으로 결합하는 **시맨틱 히스토리 최적화(Semantic History Optimization)** 기술입니다. 개발 과정에서 발생하는 자잘한 기록들을 정리하여 프로젝트의 전체적인 흐름을 명확하게 만드는 데 목적이 있습니다.

주요 내용과 핵심 포인트는 다음과 같습니다.

### 1. Squash를 사용하는 이유

- **히스토리 가독성 향상**: "오타 수정", "작업 중(WIP)", "테스트 추가"와 같이 파편화된 커밋들을 하나로 합쳐 전체 변경 내역을 한눈에 파악하기 쉽게 만듭니다.
- **시맨틱 무결성(Semantic Integrity)**: 각 커밋이 하나의 독립적이고 테스트가 완료된 기능 단위(Feature)를 대표하도록 보장합니다.
- **디버깅 용이성**: 히스토리가 단순해지면 `git bisect` 등을 이용해 버그가 도입된 시점을 추적하는 과정이 훨씬 간결해집니다.

### 2. 주요 메커니즘

- **로컬에서 커밋, 푸시 전 Squash**: 로컬 환경에서는 자유롭게 자주 커밋하고, 공용 브랜치(main/master)에 푸시하기 직전에 Squash를 수행하여 깔끔한 기록만 남기는 것이 권장됩니다.
- **Merge Squash**: `git merge --squash <branch>` 명령어를 사용하여 특정 브랜치의 모든 변경 사항을 대상 브랜치에 하나의 새로운 커밋으로 합쳐서 병합할 수 있습니다.

### 3. Squash의 효과 (예시)

- **수행 전**:
  - `Commit A`: 기능 기초 설계
  - `Commit B`: 오타 수정
  - `Commit C`: 버그 수정 및 완성
- **수행 후**:
  - `Commit A'`: [Feature] 기능 구현 완료

### 4. 핵심 원칙

> **"로컬에서는 자주 커밋하되, 공용 브랜치로 보내기 전에는 반드시 Squash하여 시맨틱한 히스토리를 구성하라."**

Squash는 단순한 정리를 넘어 팀 동료들이 프로젝트의 변경 사항을 논리적인 단위로 이해할 수 있도록 돕는 협업의 필수적인 과정입니다.

## Conflict Resolution: Textual vs. Semantic

Git의 병합 과정에서 발생하는 충돌은 크게 시스템이 감지할 수 있는 **Textual Conflict**와 시스템은 정상으로 판단하지만 논리적 오류를 야기하는 **Semantic Conflict**로 나뉩니다.

### 1. Textual Conflict

Git의 병합 알고리즘이 자동으로 해결할 수 없는 물리적인 코드의 겹침 현상입니다.

- **발생 원인**: 동일한 파일의 같은 라인이나 인접한 영역을 두 명 이상의 개발자가 서로 다르게 수정하고 병합을 시도할 때 발생합니다.
- **Git의 대응**: 자동 병합(Automatic Merge) 프로세스를 즉시 중단하고 '상태 실패'를 선언합니다.
- **해결 방식**: Git은 해당 파일 내에 충돌 표시자(`<<<<<<<`, `=======`, `>>>>>>>`)를 삽입합니다. 개발자는 이 표식을 보고 어떤 코드를 남길지 직접 판단하여 수정한 뒤, 다시 스테이징(`git add`)하고 커밋해야 합니다.

### 2. Semantic Conflict

Git의 관점에서는 병합이 성공적으로 완료되었으나, 프로그램의 논리적 흐름이나 기능 측면에서 오류가 발생하는 '잠재적 위험' 상황입니다.

- **발생 원인**: 각기 다른 파일이나 서로 다른 함수를 수정하여 텍스트 상으로는 겹치지 않지만, 실행 시 서로의 로직을 손상시키는 경우입니다.
  - _예시_: 한 개발자가 함수의 이름을 변경하고, 다른 개발자가 이전 이름의 함수를 호출하는 코드를 작성하여 병합하면, Git은 두 수정을 모두 반영하지만 프로그램은 컴파일 에러나 런타임 에러를 일으킵니다.
- **위험성**: Git은 이 상황을 충돌로 인식하지 못하므로 아무런 경고 없이 병합을 완료합니다. 따라서 감지하기가 매우 까다롭고 위험합니다.
- **해결 및 방지책**: Git 도구만으로는 해결할 수 없으며, **자동화된 테스트(Automated Testing)** 체계가 필수적입니다.
  - **Unit Test**: 개별 함수의 논리적 정합성 확인
  - **Integration Test**: 병합 후 모듈 간 상호작용 확인
  - **CI/CD Pipeline**: 병합 시점에 자동으로 테스트를 수행하여 논리적 결함을 즉시 탐지

### 요약 비교

| 구분           | Textual Conflict            | Semantic Conflict                  |
| :------------- | :-------------------------- | :--------------------------------- |
| **감지 주체**  | **Git 엔진** (자동 감지)    | **개발자 및 테스트 시스템**        |
| **원인**       | 동일 라인의 중복 수정       | 코드 간의 논리적 연관성 파괴       |
| **Git의 상태** | Merge Failure (중단)        | Clean Merge (성공으로 간주)        |
| **해결 도구**  | 수동 편집 및 충돌 마커 제거 | 단위/통합 테스트, CI/CD 파이프라인 |

## reset

Git의 **`reset`**은 특정 커밋으로 상태를 되돌리며 HEAD, Index, Working Directory의 상태를 정밀하게 제어하는 기술입니다. 각 옵션의 차이는 '어느 단계까지 이전 상태로 동기화할 것인가'에 달려 있습니다.

### 1. Reset의 3단계 메커니즘

`git reset <commit>` 명령이 실행될 때, Git은 내부적으로 다음 세 단계를 순차적으로 수행하며 옵션에 따라 중단 지점이 달라집니다.

1.  **Step 1 (HEAD 이동):** 현재 브랜치가 가리키는 커밋 포인터를 대상 커밋으로 옮깁니다. (`--soft`는 여기서 멈춤)
2.  **Step 2 (Index 업데이트):** Staging Area의 내용을 대상 커밋의 상태와 일치시킵니다. (`--mixed`는 여기서 멈춤)
3.  **Step 3 (Working Directory 업데이트):** 실제 디스크 상의 파일들을 대상 커밋의 내용으로 덮어씁니다. (`--hard` 시 수행)

### 2. 주요 옵션별 상세 분석

#### ① --soft

- **범위:** HEAD 포인터만 이동합니다.
- **특징:** Index(Staging Area)와 Working Directory는 그대로 유지됩니다.
- **용도:** 방금 한 커밋을 취소하고, 변경 사항은 그대로 둔 채 다시 커밋 메시지를 작성하거나 여러 커밋을 하나로 묶고 싶을 때 사용합니다.
- **결과:** `git status`를 확인하면 기존의 변경 사항들이 여전히 'Changes to be committed' 상태로 남아 있습니다.

#### ② --mixed (기본값)

- **범위:** HEAD 이동 + Index 업데이트.
- **특징:** Working Directory의 파일들은 건드리지 않습니다.
- **용도:** 잘못 Staging된 파일들을 내리고 싶거나(Unstage), 커밋 히스토리를 취소하면서 코드 수정은 계속 이어가고 싶을 때 사용합니다.
- **결과:** 변경 사항들이 'Changes not staged for commit' 상태로 내려옵니다.

#### ③ --hard

- **범위:** HEAD 이동 + Index 업데이트 + Working Directory 업데이트.
- **특징:** 대상 커밋 이후의 모든 변경 사항을 완전히 삭제하고 해당 시점으로 강제 동기화합니다.
- **주의사항:** **데이터 손실 위험**이 큽니다. 추적되지 않은(Untracked) 파일을 제외하고, 아직 커밋하지 않은 모든 작업 내역이 영구적으로 사라집니다.
- **용도:** 현재 작업을 완전히 폐기하고 특정 과거 시점으로 깨끗하게 되돌아가고 싶을 때 사용합니다.

### 3. 상황별 요약 비교표

| 옵션        | HEAD 이동 | Index 업데이트 | Working Directory 수정 | 작업 상태 보존           |
| :---------- | :-------: | :------------: | :--------------------: | :----------------------- |
| **--soft**  |     O     |       X        |           X            | **Staged** 상태로 보존   |
| **--mixed** |     O     |       O        |           X            | **Unstaged** 상태로 보존 |
| **--hard**  |     O     |       O        |           O            | **모두 삭제** (주의)     |

### 4. 핵심 주의사항: Public History Truncation

`reset`은 히스토리를 아예 삭제하거나 재작성하는 방식입니다. 따라서 이미 원격 저장소(Shared Remote)에 **Push된 커밋**에 대해서는 `reset`을 사용해서는 안 됩니다. 협업 중인 다른 팀원들의 로컬 환경과 DAG 구조가 일치하지 않게 되어 심각한 충돌을 야기하기 때문입니다. 공개된 히스토리의 롤백이 필요할 때는 반드시 `revert`를 사용해야 합니다.

## Revert

Git에서 **Revert**는 이미 발생한 커밋의 변경 사항을 되돌리기 위해 사용하는 **안전한 트랜잭션 롤백(Safe Transaction Rollback)** 메커니즘입니다. 단순히 히스토리를 삭제하는 `reset`과 달리, 기존 이력을 보존하면서 반대되는 작업을 수행합니다.

### 1. 동작 메커니즘: 역패치(Inverse Patch)

`git revert <commit>` 명령을 실행하면 Git은 해당 커밋에서 발생한 모든 변화를 수학적으로 계산합니다. 만약 특정 라인에 텍스트가 추가되었다면 이를 삭제하고, 삭제되었다면 다시 추가하는 식의 **역패치($x^{-1}$)**를 생성합니다. 이 결과물은 새로운 커밋 객체로 생성되어 브랜치의 끝(End)에 추가됩니다.

### 2. Reset과의 핵심 차이점

공개된 저장소에서 히스토리의 정체성을 유지하는 데 있어 `revert`는 필수적입니다.

| 비교 항목          | `git reset`                                      | `git revert`                                             |
| :----------------- | :----------------------------------------------- | :------------------------------------------------------- |
| **히스토리 변화**  | 특정 지점 이후의 커밋 이력을 삭제(Truncation)함. | 기존 이력을 유지하며 새로운 '반전 커밋'을 추가함.        |
| **사용 권장 환경** | 로컬 전용, 아직 Push 하지 않은 개인 브랜치.      | **공용/공유 브랜치(Public Branch)**.                     |
| **데이터 무결성**  | 협업 중인 다른 노드의 DAG 구조를 파괴할 수 있음. | 분산 환경의 합의(Distributed Consensus)를 깨뜨리지 않음. |

### 3. 주요 특징 및 이점

- **히스토리 보존**: "무엇이 잘못되었고, 어떻게 수정되었는지"에 대한 전체 맥락을 기록으로 남길 수 있습니다.
- **충돌 관리**: Revert 과정에서도 다른 커밋과의 연관성에 따라 **Textual Conflict**가 발생할 수 있으며, 이때 개발자는 수동으로 충돌을 해결해야 합니다.
- **유연성**: 특정 시점의 커밋만 골라서 되돌릴 수 있으므로, 이미 여러 커밋이 진행된 상태에서 중간에 실수한 부분만 취소할 때 매우 유용합니다.

### 4. 실행 예시

1.  `git log --graph`를 통해 되돌릴 커밋의 해시값을 확인합니다.
2.  `git revert <commit_hash>` 명령을 입력합니다.
3.  자동으로 생성되는 커밋 메시지(예: `Revert "고장난 기능 추가"`)를 확인하고 저장합니다.
4.  새로운 커밋이 추가되었으므로 안전하게 `push`하여 동료들과 공유합니다.

공용 브랜치에서 잘못된 코드가 병합되었을 때, 다른 팀원들의 작업 흐름을 방해하지 않고 문제를 해결할 수 있는 가장 표준적인 방법입니다.

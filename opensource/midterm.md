## 오픈소스 라이선스 카테고리

### 1. 허용적 라이선스 (Permissive Licenses)

이 범주의 라이선스는 소프트웨어 사용, 수정, 배포에 있어 제약이 매우 적습니다. 개발자의 권리를 최소한으로 제한하며, 기업들이 독점 소프트웨어를 개발할 때 선호하는 방식입니다.

- **핵심 요구사항**: 원저작자의 저작권 고지(Copyright Notice)와 라이선스 문구 포함.
- **주요 특징**: 수정된 코드를 오픈소스로 공개할 의무가 없으며, 상업적 목적으로 활용하거나 폐쇄적인 라이선스로 전환하는 것이 비교적 자유롭습니다.
- **대표 예시**:
  - **MIT**: 가장 단순하고 대중적인 라이선스로, 거의 모든 행위를 허용합니다.
  - **Apache 2.0**: MIT와 유사하지만, 특허권 관련 조항과 변경 로그 작성을 명시하여 기업 환경에 적합합니다.
  - **BSD**: MIT와 유사하며, 저작자의 이름을 홍보에 사용하지 못하게 하는 등의 부가 조항이 포함되기도 합니다.

### 2. 카피레프트 라이선스 (Copyleft Licenses)

저작권을 기반으로 정보의 공유를 강제하는 개념입니다. "바이러스성(Viral)" 라이선스라고도 불리는데, 이는 해당 라이선스가 적용된 코드를 사용하면 그 결과물도 동일한 라이선스를 따라야 하기 때문입니다.

- **핵심 요구사항**: 수정된 버전을 배포할 때 반드시 동일한 라이선스로 소스 코드를 공개해야 함.
- **강한 카피레프트 (Strong Copyleft)**: 프로젝트의 일부라도 해당 코드가 포함되면 전체 프로젝트 소스 코드를 동일 라이선스로 공개해야 합니다.
  - **예시**: **GPL (GNU General Public License)** v2/v3.
- **약한 카피레프트 (Weak Copyleft)**: 라이브러리 형태로 결합하여 사용할 경우, 라이브러리 자체를 수정한 것이 아니라면 전체 프로젝트 소스를 공개할 의무가 없습니다.
  - **예시**: **LGPL (Lesser GPL)**.

### 3. 비교 요약

| 구분               | Permissive (MIT, Apache)   | Copyleft (GPL)              | Weak Copyleft (LGPL)                      |
| :----------------- | :------------------------- | :-------------------------- | :---------------------------------------- |
| **소스 공개 의무** | 없음                       | 반드시 공개                 | 수정된 라이브러리만 공개                  |
| **조합 자유도**    | 매우 높음                  | 낮음 (동일 라이선스만 가능) | 중간                                      |
| **주요 목적**      | 광범위한 코드 채택 및 사용 | 생태계 전체의 오픈소스 유지 | 라이브러리 활용과 독점 소프트웨어 간 타협 |

선택의 기준은 명확합니다. 내 코드가 널리 쓰이길 원한다면 **Permissive**를, 내 코드를 활용해 만든 모든 파생 작업물이 계속 오픈소스로 남길 원한다면 **GPL**을 선택하는 것이 기술적·법률적 전략의 핵심입니다.

## The Four Fundamental Objects

### 1. Blob (Binary Large Object)

- **역할:** 파일의 실제 데이터를 저장하는 객체입니다.
- **특징:** 파일명이나 권한 같은 메타데이터는 포함하지 않고 오직 **Raw File Content**만 보관합니다. 동일한 내용의 파일은 해시값이 같으므로 중복 저장되지 않아 저장 효율성이 높습니다.

### 2. Tree

- **역할:** 디렉토리 구조를 표현하는 객체입니다.
- **특징:** 파일 시스템의 디렉토리처럼 작동하며, 하위의 **Blob**이나 또 다른 **Tree**를 가리키는 포인터(해시값), 파일명, 모드 등을 포함합니다. 특정 파일의 내용이 바뀌면 해당 파일의 Blob 해시가 변하고, 이를 포함하는 상위 Tree들의 해시값도 연쇄적으로 변경됩니다.

### 3. Commit

- **역할:** 프로젝트의 특정 시점의 전체 상태(Snapshot)를 정의합니다.
- **특징:** 다음의 데이터를 포함하여 데이터의 무결성과 히스토리를 보장합니다.
  - **Root Tree:** 해당 시점의 프로젝트 최상위 디렉토리 포인터.
  - **Metadata:** 작성자(Author), 커밋 날짜, 커밋 메시지.
  - **Parent Pointer:** 이전 커밋의 해시값을 가리켜 커밋들이 연결된 **DAG(Directed Acyclic Graph)** 구조를 형성하게 합니다.

### 4. Tag

- **역할:** 특정 커밋에 대해 고유한 이름을 부여하는 영구적인 참조입니다.
- **특징:** 보통 `v1.0`과 같은 릴리스 지점을 표시할 때 사용하며, 브랜치와 달리 한 번 생성되면 특정 커밋을 가리키는 포인터가 변하지 않습니다.

### 객체 분석 및 접근 방법

이러한 객체들은 zlib으로 압축되어 `.git/objects` 디렉토리에 저장되며, SHA-1 알고리즘에 의해 생성된 **160-bit(40자 16진수)** 해시값이 각 객체의 고유한 키(ID)가 됩니다.

- `git cat-file -t <hash>`: 객체의 타입(blob, tree, commit 등) 확인
- `git cat-file -p <hash>`: 객체의 실제 내용(내부 데이터) 출력

## Git의 이력 관리 및 롤백 전략

### 1. Merge (병합)

분기된 이력을 통합하는 가장 기본적인 메커니즘입니다.

- **Fast-Forward (FF):** 현재 브랜치의 조상이 대상 브랜치일 경우, 별도의 커밋 생성 없이 브랜치 포인터만 대상 커밋으로 이동시킵니다.
- **3-Way Merge:** 두 브랜치가 공통 조상에서 분기된 후 각자 진행되었을 때 사용됩니다. 공통 조상과 각 브랜치의 끝단(Tip)을 비교하여 새로운 'Merge Commit'을 생성하며 병합합니다.

### 2. Rebase (베이스 재설정)

브랜치의 기점(Base)을 다른 커밋으로 옮겨 이력을 선형적(Linear)으로 재구성합니다.

- **메커니즘:** 브랜치의 고유 커밋들을 임시 패치로 추출한 후, 타겟 브랜치의 최신 커밋 위에서 순차적으로 다시 적용합니다.
- **주의사항:** 커밋 식별자(Hash)가 변경되므로, 이미 원격 저장소에 Push된 공통 커밋에 대해서는 수행하지 않는 것이 원칙입니다.

### 3. Squash (커밋 합치기)

여러 개의 커밋을 하나의 커밋으로 결합하여 이력의 의미적 무결성을 높이는 기법입니다.

- **활용:** 로컬에서 작업한 자잘한 'WIP(Work In Progress)' 커밋들이나 오타 수정 이력을 하나로 합쳐, 메인 브랜치에는 완성된 기능 단위의 커밋만 남기고자 할 때 사용합니다.
- **효과:** `git bisect` 등을 이용한 디버깅 시 가독성을 높이고 히스토리를 깔끔하게 유지합니다.

### 4. Reset (로컬 상태 복구)

HEAD 포인터를 이전 커밋으로 이동시켜 이력을 특정 시점으로 되돌립니다.

- **--soft:** HEAD만 이동하며, Index와 Working Directory의 변경 사항은 유지됩니다 (커밋 직전 상태).
- **--mixed (기본값):** HEAD 이동 및 Index 초기화까지 수행합니다 (Staging 이전 상태).
- **--hard:** HEAD, Index, Working Directory를 모두 특정 커밋 상태로 강제 일치시킵니다 (미커밋 데이터 유실 주의).

### 5. Revert (공개 이력 수정)

기존 이력을 삭제하지 않고, 특정 커밋의 변경 사항을 되돌리는 '역 패치(Inverse Patch)' 커밋을 새로 생성합니다.

- **안전성:** 커밋 해시를 변조하지 않고 새로운 노드를 추가하는 방식이므로, 동료와 공유 중인 공용 브랜치에서 안전하게 실수를 취소할 수 있는 유일한 방법입니다.

### 요약 비교 테이블

| 구분       | 목적        | 대상      | 이력 형태                       |
| :--------- | :---------- | :-------- | :------------------------------ |
| **Merge**  | 이력 통합   | 공용/로컬 | 비선형 (병합 커밋 생성 가능)    |
| **Rebase** | 이력 선형화 | 로컬 전용 | 선형 (Hash 변경 발생)           |
| **Squash** | 커밋 정리   | 로컬 전용 | 단순화 (여러 커밋 -> 단일 커밋) |
| **Reset**  | 이력 절단   | 로컬 전용 | 삭제 (이후 커밋 제거)           |
| **Revert** | 이력 취소   | 공용/로컬 | 보존 (취소용 커밋 추가)         |

## Git 충돌

### 1. Textual Conflict (텍스트 충돌)

- **정의**: 동일한 파일의 같은 행이나 영역에 대해 서로 다른 변경 사항이 겹칠 때 발생하는 자동 병합 실패입니다.
- **Git의 대응**: 병합 프로세스를 중단하고 파일 내부에 `<<<<<<<`, `=======`, `>>>>>>>`와 같은 **Conflict Markers**를 주입합니다.
- **해결 방법**: 개발자가 직접 코드를 검토하여 충돌 지점을 수정하고 수동으로 커밋을 완료해야 합니다.

### 2. Semantic Conflict (세만틱/논리 충돌)

- **정의**: Git의 관점에서는 텍스트 상 겹치는 부분이 없어 병합이 성공적으로 수행되었으나, 결합된 코드가 논리적으로 오류를 일으키거나 버그를 유발하는 상태입니다.
- **특징**: Git은 파일 시스템 수준에서 동작하므로 이러한 **비정상적 논리 결합**을 감지하지 못합니다.
- **위험성**: 컴파일 에러나 런타임 버그로 이어질 수 있는 가장 치명적인 충돌 유형입니다.
- **방어 전략**: $CI/CD$ 파이프라인 내에서 유닛 테스트, 통합 테스트, E2E 테스트 등 강력한 **자동화된 테스트**를 수행하여 논리적 무결성을 검증해야 합니다.

## TDD Anti-Pattern

### 1. The Giant (거대한 테스트)

- **증상**: 하나의 테스트 메서드가 너무 많은 기능이나 시나리오를 한꺼번에 검증하려고 시도하는 경우입니다 (`testAllFeatures()`).
- **문제점**: 테스트 실패 시 정확히 어떤 어설션(Assertion)에서 문제가 발생했는지 파악하기 어렵고, 테스트의 의도가 불분명해져 '실행 가능한 명세서'로서의 가치를 상실합니다.
- **해결책**: **"One Test, One Logical Concept"** 원칙을 준수해야 합니다. Given-When-Then 패턴을 사용하여 테스트 구조를 명확히 분리합니다.

### 2. The Brittle Test (취약한 테스트)

- **증상**: 프로덕션 코드의 내부 구현 세부 사항(Implementation Details)에 과도하게 의존하는 테스트입니다.
- **예시**: UI 버튼의 CSS 클래스 이름 변경, 내부 알고리즘의 특정 수행 순서, 혹은 프라이빗(private) 메서드 호출 여부를 검증하는 경우입니다.
- **문제점**: 기능상 문제가 없음에도 리팩토링만으로 테스트가 실패하게 되어, TDD의 안전망 역할을 저해하고 개발자의 신뢰를 떨어뜨립니다.
- **해결책**: **"Test Behavior, Not Implementation"** 원칙에 집중합니다. 객체의 공개 API를 통해 관찰 가능한 상태 변화나 반환값만을 검증해야 합니다.

### 3. The Slowpoke (느림보 테스트)

- **증상**: 네트워크, 데이터베이스(DB), 파일 시스템 등 외부 자원에 직접 접근하여 실행 시간이 오래 걸리는 테스트입니다.
- **문제점**: TDD의 핵심인 '빠른 피드백 루프'를 파괴합니다. 테스트 실행이 느려지면 개발자는 심리적 장벽을 느껴 테스트를 자주 실행하지 않게 됩니다.
- **해결책**: **테스트 더블(Mocks, Stubs 등)**을 적극적으로 활용합니다. 순수 로직 검증은 단위 테스트(Unit Test)에서 처리하고, 느린 테스트(통합/E2E 테스트)는 격리하여 $CI$ 파이프라인의 특정 단계에서만 실행하도록 구성합니다.

## **Refactoring: Principles, Smells, and Techniques**

### **1. 설계 원칙: SOLID**

객체 지향 설계(OOD)의 5가지 핵심 원칙으로, 리팩토링 시 "더 나은 설계"를 위한 가이드라인을 제공합니다. 이를 통해 높은 응집도(High Cohesion)와 낮은 결합도(Low Coupling)를 가진 유연한 시스템을 구축하는 것이 목표입니다.

- **S (SRP):** 단일 책임 원칙. 클래스는 단 하나의 변경 이유(책임)만 가져야 합니다.
- **O (OCP):** 개방-폐쇄 원칙. 확장에는 열려 있고 수정에는 닫혀 있어야 합니다.
- **L (LSP):** 리스코프 치환 원칙. 하위 타입은 상위 타입을 대체할 수 있어야 합니다.
- **I (ISP):** 인터페이스 분리 원칙. 사용하지 않는 메서드에 의존하도록 강제해서는 안 됩니다.
- **D (DIP):** 의존역전 원칙. 고수준 모듈은 저수준 모듈이 아닌 추상화에 의존해야 합니다.

### **2. 코드 스멜 (Code Smells)**

버그는 아니지만 시스템의 설계 결함을 시사하는 징후들로, 마틴 파울러는 이를 5가지 카테고리로 분류했습니다.

- **Bloaters (비대해진 코드):** 메서드나 클래스가 너무 커진 상태 (예: Long Method, Large Class, Primitive Obsession, Data Clumps).
- **OO Abusers (객체 지향 오용):** 상속이나 조건문을 잘못 사용한 경우 (예: Excessive if/elif/else, Refused Bequest).
- **Change Preventers (수정 방해물):** 코드 변경 시 여러 곳을 동시에 수정하게 만드는 구조 (예: Divergent Change, Shotgun Surgery).
- **Dispensables (불필요한 요소):** 삭제해도 무방한 코드 (예: Duplicated Code, Dead Code, 주석으로 설명된 로직).
- **Couplers (결합자):** 클래스 간 과도한 의존성 (예: Feature Envy, Message Chains, Middle Man).

### **3. 주요 리팩토링 기법**

코드 스멜을 제거하고 품질을 높이기 위한 구체적인 방법론입니다.

- **메서드 정리:** 긴 메서드를 작고 명확하게 분할 (Extract Method, Inline Method).
- **기능 이동:** 책임을 적절한 클래스로 재배치 (Move Method, Extract Class).
- **데이터 조직화:** 데이터 표현 방식 개선 (Replace Magic Number, Encapsulate Field).
- **조건부 로직 단순화:** 복잡한 if 문 등을 명확하게 개선 (Decompose Conditional).
- **다형성 활용 (Replace Conditional with Polymorphism):** 조건문을 인터페이스나 상속을 이용한 다형성 구조로 변환하여 OCP를 준수하도록 개선.

### **4. 예시: Feature Envy와 Extract Method**

- **Feature Envy 사례:** `Order` 클래스의 메서드가 자신의 데이터보다 `Customer` 클래스의 데이터를 더 많이 참조할 때, 해당 메서드를 `Customer` 클래스로 이동시켜 결합도를 낮춥니다.
- **Extract Method 사례:** `print_owing` 메서드 내에 배너 출력, 계산, 상세 정보 출력 로직이 섞여 있을 때, 각 로직을 독립된 private 메서드로 추출하여 가독성과 재사용성을 높입니다.

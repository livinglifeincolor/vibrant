## 주요 내용 정리

### 1. 리팩터링(Refactoring)의 본질

- **정의:** 소프트웨어의 외부적 동작(External Behavior)은 유지하며, 내부 구조(Internal Structure)를 개선하여 품질을 높이는 규율 있는 프로세스입니다.
- **목적:** 소프트웨어 엔트로피(무질서도) 증가로 인한 '코드 부패(Code Rot)'를 방지하고, 유지보수 비용을 낮추는 예방적 유지보수 활동입니다.
- **시기:** 기능 추가 전(준비), 코드 이해를 돕기 위해(이해), 발견 즉시(보이스카우트 규칙), 혹은 계획된 기술 부채 해결 시 수행합니다.
- **주의사항:** 단순 재작성(Rewrite), 기능 추가, 성급한 최적화, 테스트 없는 수정은 리팩터링이 아닙니다.

### 2. 설계 원칙: SOLID

리팩터링의 지향점이 되는 객체지향 설계의 5대 원칙입니다.

- **S (SRP):** 단일 책임 원칙 (하나의 클래스는 하나의 변경 이유만 가져야 함)
- **O (OCP):** 개방-폐쇄 원칙 (확장에는 열려 있고 수정에는 닫혀 있어야 함)
- **L (LSP):** 리스코프 치환 원칙 (서브타입은 언제나 기반 타입으로 교체 가능해야 함)
- **I (ISP):** 인터페이스 분리 원칙 (사용하지 않는 메서드에 의존하도록 강제하지 않음)
- **D (DIP):** 의존성 역전 원칙 (구체화가 아닌 추상화에 의존해야 함)

### 3. 코드 스멜(Code Smells) 및 해결 기법

설계상의 잠재적 문제를 나타내는 징후들과 그 해결책입니다.

- **Bloaters (비대해진 것들):** 긴 메서드, 거대 클래스, 데이터 뭉치 등
- **OO Abusers (객체지향 남용):** 과도한 switch/if 문, 거부된 유산 등
- **Change Preventers (수정 방해물):** 발산적 변경, 산탄총 수술 등
- **Dispensables (불필요한 것들):** 중복 코드, 주석(설명용), 죽은 코드 등
- **Couplers (결합자):** 기능 욕심(Feature Envy), 메시지 체인 등
- **주요 기법:** 메서드 추출(Extract Method), 조건부를 다형성으로 교체, 필드 이동 등

### 4. AI 기반 리팩터링 (AI-Driven Refactoring)

AI 시대의 새로운 개발 패러다임을 제시합니다.

- **새로운 기술 부채:** AI가 생성한 코드는 맥락이 결여되거나 오버엔지니어링될 수 있어 리팩터링의 중요성이 더욱 커졌습니다.
- **워크플로우:** 개발자(전략 및 최종 결정)와 AI(분석 및 실행)의 협업 구조입니다.
- **TDD의 역할:** AI가 수행한 리팩터링의 논리적 무결성을 검증하는 최후의 방어선입니다.
- **프롬프트 엔지니어링:** 전략적 옵션 요청, 디자인 패턴 적용 명령, 복잡한 로직 개선 등 구체적인 지시가 필요합니다.

## Refactoring

### 리팩터링의 정의

리팩터링은 단순히 코드를 수정하는 것이 아니라, 마틴 파울러(Martin Fowler)가 정의한 **'규율 있는 프로세스'**입니다.

- **불변의 원칙:** 소프트웨어의 **외부적인 관찰 가능한 동작**은 절대 바뀌지 않아야 합니다. API 시그니처, 반환 값, 성능 특성 등이 100% 동일하게 유지되어야 함을 보장합니다.
- **내부적 개선:** 클래스의 책임 분산, 메서드 응집도 향상, 모듈 간 결합도 완화, 변수명 명확화 등 내부 디자인 품질을 점진적으로 향상시킵니다.
- **관심사 분리:** 새로운 기능을 추가하거나 버그를 잡는 행위와는 완전히 분리된 별개의 활동으로 취급합니다.

### 리팩터링을 하는 이유: 소프트웨어 엔트로피

소프트웨어는 시간이 지남에 따라 자연스럽게 무질서해지는 경향이 있습니다.

- **소프트웨어 엔트로피 법칙:** 열역학 제2법칙처럼, 지속적인 요구사항 변경과 수정이 가해지면 시스템의 복잡도와 무질서는 필연적으로 증가합니다.
- **코드 부패 (Code Rot):** 엔트로피 증가로 인해 구조가 점차 붕괴되는 현상입니다. 이는 버그 발생 확률을 기하급수적으로 높이고 유지보수 비용을 폭증시킵니다.
- **엔지니어링적 저항:** 리팩터링은 이러한 자연적인 부패에 저항하여 시스템의 건강과 수명을 유지하고, 향후 변경에 드는 비용을 낮추기 위한 의식적이고 지속적인 노력입니다. 일종의 **'예방 정비'**와 같습니다.

### 리팩터링 수행 시점

리팩터링은 특정 시기에만 하는 것이 아니라 상황에 맞춰 유연하게 수행합니다.

- **준비용 리팩터링 (Preparatory):** 새로운 기능을 구현하기 직전, 해당 기능을 더 쉽고 안전하게 추가할 수 있도록 주변 코드를 먼저 정리합니다.
- **이해용 리팩터링 (Comprehension):** 복잡한 레거시 코드를 파악할 때, 변수 이름을 바꾸거나 관련 코드를 모으는 등 구조를 변경하며 코드의 의도를 명확히 이해합니다.
- **보이스카우트 규칙 (Litter-Pickup):** 코드를 읽다가 발견한 작은 문제(스멜)를 즉시 수정합니다. "캠핑장은 올 때보다 더 깨끗하게 해놓고 떠나야 한다"는 원칙을 따릅니다.
- **계획된 리팩터링 (Planned):** 기술 부채가 너무 심각할 때, 팀원들과 목표를 설정하고 특정 기간(예: 1~2주 스프린트) 동안 집중적으로 개선합니다.

### 리팩터링이 아닌 것: 안티 패턴

리팩터링과 혼동해서는 안 되는 위험한 활동들입니다.

- **재작성 (Rewrite):** 점진적 개선이 아니라 모든 것을 처음부터 다시 만드는 '빅뱅' 방식입니다. 실패 위험이 크고 기존의 암묵적인 지식을 잃어버릴 수 있습니다.
- **기능 추가 (Feature Addition):** 시스템의 외부 동작을 조금이라도 변화시키는 작업은 리팩터링이 아닙니다.
- **성급한 최적화 (Premature Optimization):** 프로파일링을 통해 병목 지점을 확인하지 않은 채, 추측만으로 성능을 개선하려는 시도입니다.
- **테스트 없는 수정 (Untested Modification):** 동작 보존을 증명할 테스트가 없다면 그것은 리팩터링이 아니라 **'파괴적인 도박'**에 불과합니다. 가장 위험한 행위로 간주됩니다.

## SOLID 설계 원칙

### 1. SRP: Single Responsibility Principle (단일 책임 원칙)

> **"클래스는 변경해야 할 이유가 단 하나여야 한다."**

클래스는 하나의 액터(Actor)에 대해서만 책임을 져야 합니다. 여러 책임이 섞여 있으면 한 기능을 수정할 때 연관 없는 기능까지 영향을 받을 수 있습니다.

#### [예시 코드]

- **Before (위반):** `Report` 클래스가 콘텐츠 생성, HTML 렌더링, DB 저장 책임을 모두 가짐.

```python
class Report:
    def create_content(self): return "Report Content"
    def render_to_html(self, content): return f"<h1>{content}</h1>"
    def save_to_database(self, content): print(f"'{content}' saved")
```

- **After (준수):** 책임을 분리하여 각각의 전용 클래스로 추출.

```python
class Report:
    def create_content(self): return "Report Content"

class HtmlRenderer:
    def render(self, content): return f"<h1>{content}</h1>"

class ReportRepository:
    def save(self, content): print(f"'{content}' saved")
```

### 2. OCP: Open/Closed Principle (개방-폐쇄 원칙)

> **"소프트웨어 엔티티는 확장에는 열려 있어야 하고, 수정에는 닫혀 있어야 한다."**

새로운 기능을 추가할 때 기존 코드를 수정하지 않고 확장을 통해 기능을 수행해야 합니다. 주로 인터페이스나 추상 클래스를 통해 구현합니다.

#### [예시 코드]

- **Before (위반):** 새로운 결제 방식이 추가될 때마다 `if/elif` 문을 계속 수정해야 함.

```python
def process_payment(payment_type, amount):
    if payment_type == 'credit_card':
        print(f"Processing credit card: {amount}")
    elif payment_type == 'bank_transfer':
        print(f"Processing bank transfer: {amount}")
```

- **After (준수):** 전략 패턴(Strategy Pattern)을 사용하여 결제 로직을 캡슐화하고 확장 가능하게 구성.

```python
class PaymentStrategy(ABC):
    def process(self, amount): pass

class CreditCardStrategy(PaymentStrategy):
    def process(self, amount): print(f"Processing credit card: {amount}")

class BankTransferStrategy(PaymentStrategy):
    def process(self, amount): print(f"Processing bank transfer: {amount}")

def process_payment(strategy: PaymentStrategy, amount):
    strategy.process(amount)
```

### 3. LSP: Liskov Substitution Principle (리스코프 치환 원칙)

> **"서브타입은 언제나 자신의 기반 타입(Base Type)으로 교체할 수 있어야 한다."**

자식 클래스는 부모 클래스의 규약(Behavior)을 위반해서는 안 됩니다. 단순히 문법적 상속이 아니라, 논리적으로 부모를 대신할 수 있어야 합니다.

#### [예시 코드]

- **Before (위반):** `Square`가 `Rectangle`을 상속받으면, 가로/세로를 독립적으로 설정하는 직사각형의 동작 모델이 깨짐.

```python
class Rectangle:
    def __init__(self, width, height): self._width, self._height = width, height
    def set_width(self, width): self._width = width
    def set_height(self, height): self._height = height
    def get_area(self): return self._width * self._height

class Square(Rectangle):
    def set_width(self, width): self._width = self._height = width
    def set_height(self, height): self._width = self._height = height
```

- **After (준수):** 상속 관계를 제거하고 별도의 클래스로 분리하거나 공통 인터페이스만 공유.

```python
class Rectangle:
    def __init__(self, width, height): self._width, self._height = width, height
    def set_width(self, width): self._width = width
    def set_height(self, height): self._height = height
    def get_area(self): return self._width * self._height

class Square:
    def __init__(self, side): self._side = side
    def get_area(self): return self._side ** 2
```

### 4. ISP: Interface Segregation Principle (인터페이스 분리 원칙)

> **"클라이언트는 자신이 사용하지 않는 메서드에 의존하도록 강제되어서는 안 된다."**

범용적인 '뚱뚱한 인터페이스(Fat Interface)'보다는 클라이언트에 특화된 여러 개의 구체적인 인터페이스가 낫습니다.

#### [예시 코드]

- **Before (위반):** `RobotWorker`는 먹을 필요가 없지만 `Worker` 인터페이스 때문에 `eat()` 메서드를 구현해야 함.

```python
class Worker(ABC):
    def work(self): pass
    def eat(self): pass

class RobotWorker(Worker):
    def work(self): print("Working...")
    def eat(self): pass  # 불필요한 구현 발생
```

- **After (준수):** 역할을 분리하여 필요한 인터페이스만 상속받음.

```python
class Workable(ABC):
    def work(self): pass

class Eatable(ABC):
    def eat(self): pass

class RobotWorker(Workable):
    def work(self): print("Working...")
```

### 5. DIP: Dependency Inversion Principle (의존성 역전 원칙)

> **"고수준 모듈은 저수준 모듈에 의존해서는 안 되며, 둘 다 추상화에 의존해야 한다."**

구체적인 구현체(MySQL, EmailService 등)에 직접 의존하지 말고, 인터페이스나 추상 클래스 같은 추상화에 의존하여 결합도를 낮추어야 합니다.

#### [예시 코드]

- **Before (위반):** `PasswordReminder` 클래스가 구체적인 `MySQLConnection`에 직접 의존함.

```python
class MySQLConnection:
    def connect(self): print("MySQL connected")

class PasswordReminder:
    def __init__(self):
        self.db_connection = MySQLConnection() # 직접 의존 (결합도 높음)
    def remind(self):
        self.db_connection.connect()
```

- **After (준수):** 인터페이스를 통해 의존성을 주입(Dependency Injection)받음.

```python
class DBConnection(ABC):
    def connect(self): pass

class MySQLConnection(DBConnection):
    def connect(self): print("MySQL connected")

class PasswordReminder:
    def __init__(self, db_connection: DBConnection):
        self.db_connection = db_connection # 추상화에 의존
    def remind(self):
        self.db_connection.connect()
```

#### 요약

SOLID 원칙을 적용하면 **응집도는 높아지고(High Cohesion)**, **결합도는 낮아져(Low Coupling)** 변화에 유연하게 대응할 수 있는 견고한 시스템을 구축할 수 있습니다. 각 원칙은 독립적이지 않으며, 상호보완적으로 작용하여 전체적인 코드 품질을 결정합니다.

## Code Smells

코드 스멜(Code Smells)은 프로그램의 작동을 방해하는 버그는 아니지만, 소프트웨어의 유지보수성을 저해하고 잠재적인 설계 결함을 암시하는 징후들입니다. 마틴 파울러(Martin Fowler)가 정의한 5가지 범주를 중심으로 세부 내용을 정리해 드립니다.

### 1. Bloaters (비대해진 것들)

코드가 시간이 지나면서 거대해져서 다루기 힘들어진 경우입니다.

- **Long Method (긴 메서드):** 하나의 메서드가 너무 많은 일을 수행하여 응집도가 낮은 상태입니다.
- **Large Class (거대 클래스):** 하나의 클래스가 너무 많은 책임(SRP 위반)을 가지고 있어 관리가 어렵습니다.
- **Primitive Obsession (기본 타입 집착):** 전화번호, 이메일 주소 등 도메인 개념을 객체로 만들지 않고 `str`, `int` 같은 기본 자료형으로만 처리하는 현상입니다.
- **Data Clumps (데이터 뭉치):** 여러 곳에서 항상 함께 전달되는 매개변수 그룹입니다. 이들은 별도의 객체로 추출되어야 합니다.

### 2. Object-Orientation Abusers (객체지향 남용)

객체지향 설계 원칙을 잘못 적용하거나 무시한 경우입니다.

- **Excessive if/elif/else:** 새로운 타입이 추가될 때마다 모든 조건문을 찾아 수정해야 하는 상태로, 개방-폐쇄 원칙(OCP)을 위반합니다.
- **Refused Bequest (거부된 유산):** 자식 클래스가 부모로부터 상속받은 메서드가 필요 없어 예외를 던지거나 아무 작업도 하지 않도록 재정의하는 상태입니다. 이는 리스코프 치환 원칙(LSP) 위반의 징후입니다.
- **Temporary Field (임시 필드):** 특정 알고리즘이 실행되는 동안에만 값이 할당되고 평소에는 비어 있는 인스턴스 변수가 존재하는 경우입니다.

### 3. Change Preventers (수정 방해물)

소프트웨어를 변경하려고 할 때 한 곳을 고치기 위해 너무 많은 곳을 건드려야 하는 상태입니다.

- **Divergent Change (발산적 변경):** 하나의 클래스가 서로 다른 여러 이유로 자주 수정되는 현상입니다. (SRP 위반)
- **Shotgun Surgery (산탄총 수술):** 하나의 논리적인 변경을 위해 여러 클래스의 작은 부분들을 동시에 수정해야 하는 상태입니다.
- **Parallel Inheritance Hierarchies (평행 상속 계층):** 한 클래스 계층에 하위 클래스를 만들 때, 반드시 다른 클래스 계층에도 상위와 대응하는 하위 클래스를 만들어야만 하는 경우입니다.

### 4. Dispensables (불필요한 것들)

삭제해도 시스템에 아무런 지장이 없는 코드 요소들입니다.

- **Duplicated Code (중복 코드):** 동일하거나 유사한 코드 구조가 반복되는 것으로, DRY(Don't Repeat Yourself) 원칙을 위반합니다.
- **Dead Code (죽은 코드):** 더 이상 호출되지 않거나 실행 결과에 영향을 주지 않는 코드입니다.
- **Comments (주석):** "왜"가 아니라 "무엇"을 하는지 설명하기 위해 주석을 과하게 사용한다면, 이는 코드 자체가 명확하지 않다는 신호입니다.
- **Lazy Class / Data Class:** 책임이 너무 적어 존재 가치가 없거나, 메서드 없이 데이터 홀더 역할만 하는 클래스입니다.

### 5. Couplers (결합자)

클래스 간의 관계가 지나치게 밀접하여 독립적인 수정이 어려운 상태입니다.

- **Feature Envy (기능 욕심):** 어떤 메서드가 자신이 속한 클래스보다 다른 클래스의 데이터나 메서드에 더 관심을 많이 가질 때 발생합니다.
- **Inappropriate Intimacy (부적절한 친밀함):** 한 클래스가 다른 클래스의 내부 구현(private 필드나 메서드)에 너무 깊게 관여하는 상태입니다.
- **Message Chains (메시지 체인):** `a.get_b().get_c().do_something()`과 같이 길게 연결된 호출 구조입니다. 클라이언트가 내부 구조에 너무 상세히 의존하게 됩니다.
- **Middle Man (중개자):** 클래스가 하는 일의 대부분이 다른 객체에 작업을 위임하는 것뿐인 상태입니다.

리팩터링은 이러한 **스멜을 감지**하고, **SOLID 원칙**이라는 나침반을 따라, **적절한 기법**(메서드 추출, 다형성으로 교체 등)을 적용하여 소프트웨어의 엔트로피를 낮추는 지속적인 과정입니다.

## Examples of Code Smells

### 1. Feature Envy (기능 욕심)

메서드가 자신이 속한 클래스보다 다른 클래스의 데이터나 메서드에 더 많이 접근하는 현상입니다.

#### **[Refactoring 전]**

`Order` 클래스의 메서드가 자신의 필드를 사용하기보다 `Customer` 객체의 데이터에 지나치게 의존하고 있습니다.

```python
class Customer:
    def __init__(self, address):
        self.address = address

class Order:
    def __init__(self, customer):
        self.customer = customer

    def get_shipping_cost(self):
        # 문제점: Order의 데이터는 사용하지 않고
        # 오직 Customer의 주소 정보에만 관심을 가짐 (Feature Envy)
        if self.customer.address.is_in_seoul():
            return 1000
        return 3000
```

#### **[Refactoring 후: Move Method]**

해당 로직을 데이터의 주인인 `Customer` 클래스로 이동시켜 결합도를 낮춥니다.

- **개선:** `get_shipping_cost` 메서드를 `Customer` 클래스로 이동.

### 2. Duplicated Code (중복 코드)

동일하거나 유사한 로직이 여러 곳에 존재하여 유지보수 효율을 떨어뜨리는 상태입니다.

#### **[Refactoring 전]**

`FullTimeEmployee`와 `PartTimeEmployee` 클래스 내부에 동일한 세금 계산 로직이 중복되어 기술되어 있습니다.

```python
class FullTimeEmployee:
    def get_tax(self, income):
        # 복잡한 세금 계산 로직이 직접 구현됨
        base = income * 0.8
        return base

class PartTimeEmployee:
    def get_tax(self, income):
        # 위와 동일한 복잡한 로직이 그대로 중복 발생
        base = income * 0.8
        return base - 50
```

#### **[Refactoring 후: Extract Class]**

중복되는 계산 로직을 별도의 클래스로 추출하여 단일 지점에서 관리하게 합니다.

- **개선:** 공통된 세금 로직을 `TaxCalculator` 클래스로 분리하여 재사용.

### 3. Primitive Obsession (기본 타입 집착)

도메인 개념(이메일, 전화번호, 금액 등)을 표현하기 위해 객체 대신 `str`, `int` 등 기본 자료형에만 의존하는 현상입니다.

#### **[Refactoring 전]**

이메일 유효성 검사 로직이 비즈니스 로직(메일 발송)과 섞여 있으며, 문자열(`str`) 타입만 사용하므로 검증 로직이 파편화될 위험이 큽니다.

```python
def send_welcome_email(email_address: str):
    # 문제점: 이메일 형식을 검증하는 로직이 함수 내에 산재함
    if "@" not in email_address:
        raise ValueError("Invalid email")
    # ... 메일 발송 로직
```

#### **[Refactoring 후: Replace Primitive with Object]**

기본 타입을 래핑하는 **Value Object**를 도입하여 데이터와 유효성 검증 로직을 캡슐화합니다.

```python
class EmailAddress:
    def __init__(self, address: str):
        # 생성 시점에 유효성을 검증하여 객체의 무결성 보장
        if "@" not in address:
            raise ValueError("Invalid email")
        self.address = address

    def get_domain(self):
        return self.address.split('@')[1]

def send_welcome_email(email: EmailAddress):
    # 이제 함수는 유효한 EmailAddress 객체만 전달받음을 보장받음
    ...
```

### 4. if/elif Abuse (과도한 조건문)

새로운 타입이 추가될 때마다 조건문을 수정해야 하는 상황으로, **OCP(개방-폐쇄 원칙)**를 위반합니다.

#### **[Refactoring 전]**

도형의 타입에 따라 다른 함수를 호출하는 구조로, 새로운 도형이 추가될 때마다 `draw_shape` 함수를 계속 수정해야 합니다.

```python
def draw_shape(shape):
    if shape.type == 'CIRCLE':
        draw_circle(shape.radius)
    elif shape.type == 'SQUARE':
        draw_square(shape.side)
```

#### **[Refactoring 후: Replace Conditional with Polymorphism]**

객체지향의 **다형성**을 활용하여 조건문을 제거하고 확장에 유연한 구조를 만듭니다.

```python
from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def draw(self):
        pass

class Circle(Shape):
    def draw(self):
        draw_circle(self.radius)

class Square(Shape):
    def draw(self):
        draw_square(self.side)

def draw_shape(shape: Shape):
    # 개선: 구체적인 타입을 체크하지 않고 다형적으로 메서드 호출
    shape.draw()
```

## 리팩터링의 주요 기법

### 1. 리팩터링 주요 기법 분류

리팩터링은 코드의 어떤 부분을 개선하느냐에 따라 크게 5가지 카테고리로 나뉩니다.

- **메서드 정리 (Composing Methods):** 너무 길거나 복잡한 메서드를 추출(Extract Method)하거나, 반대로 불필요한 메서드를 본문에 합치는(Inline Method) 작업입니다.
- **기능 이동 (Moving Features):** 책임이 잘못된 곳에 있는 필드나 메서드를 적절한 클래스로 옮기는 작업(Move Method, Extract Class 등)입니다.
- **데이터 조직화 (Organizing Data):** 매직 넘버를 상수로 바꾸거나 필드를 캡슐화하여 데이터 표현 방식을 개선합니다.
- **조건부 로직 단순화 (Simplifying Conditionals):** 복잡한 조건문을 분해하거나 다형성을 활용하여 논리를 명확하게 만듭니다.
- **API 단순화 (Simplifying API):** 메서드 이름을 명확하게 바꾸거나 불필요한 대리자를 숨겨 인터페이스를 개선합니다.

### 2. 핵심 기법 1: 메서드 추출 (Extract Method)

한 메서드 안에 여러 책임이 섞여 있을 때, 이를 논리적 단위로 쪼개어 가독성을 높이는 기법입니다.

#### [Before] 복합적인 기능을 수행하는 긴 메서드

```python
def print_owing(self):
    # 1. 배너 출력 (별도의 출력 로직)
    print("***** Customer Owes *****")

    # 2. 외상값 계산 (루프를 도는 계산 로직)
    outstanding = 0.0
    for order in self._orders:
        outstanding += order.get_amount()

    # 3. 세부사항 출력
    print(f"name: {self._name}")
    print(f"amount: {outstanding}")
```

#### [After] 목적에 따라 분리된 메서드들

동일한 기능을 수행하지만, `print_owing` 메서드는 전체적인 흐름만 보여주며 각 단계의 구체적 로직은 위임됩니다.

- `self._print_banner()`
- `outstanding = self._get_outstanding()`
- `self._print_details(outstanding)`

### 3. 핵심 기법 2: 조건부 로직을 다형성으로 교체

`if/elif` 문을 통해 객체의 타입별로 다른 로직을 수행하는 경우, 상속과 다형성을 이용해 코드를 깔끔하게 만드는 기법입니다.

#### [Before] 국가별 배송비 계산 (조건문 방식)

국가가 추가될 때마다 `elif` 문이 계속 늘어나야 하며, 이는 수정에 취약한 구조입니다.

```python
def calculate_shipping_fee(order):
    if order.country == 'KR':
        return order.weight * 100
    elif order.country == 'US':
        return order.weight * 300
    else:
        return order.weight * 500
```

#### [After] 추상 클래스와 하위 클래스 활용 (다형성 방식)

공통 인터페이스를 정의하고 각 국가별 계산기를 독립된 클래스로 만듭니다. 새로운 국가가 추가되어도 기존 코드를 수정할 필요 없이 새로운 클래스만 추가하면 됩니다.

- **Base Class:** `ShippingCalculator (ABC)` - 공통 인터페이스 정의
- **Subclasses:** `KrCalculator`, `UsCalculator` - 각자의 계산 로직 구현
- **Execution:** 팩토리 패턴 등을 통해 적절한 계산기 객체를 선택한 후 `calculator.calculate(order)`를 호출하여 실행합니다.

## The New Paradigm

### 1. AI 생성 코드: 기술 부채의 새로운 기원

- **생산성과 부채의 공존:** AI 코딩 어시스턴트는 개발 생산성을 획기적으로 높여주지만, 동시에 관리되지 않은 AI 생성 코드는 **새로운 형태의 기술 부채**가 될 수 있습니다.
- **맥락 결여의 위험:** AI는 단기적인 문제 해결이나 패턴화된 코드 작성에는 탁월합니다. 하지만 전체적인 소프트웨어 아키텍처나 비즈니스 도메인의 깊은 맥락을 고려하지 못한 코드를 내놓을 가능성이 큽니다.

### 2. AI 시대 리팩터링의 위상 변화

- **핵심 전략적 활동:** 이전에는 리팩터링이 선택적인 '청소' 작업이었다면, AI 시대에는 AI가 만든 코드의 장기적인 유지보수성을 보장하기 위한 **핵심 전략 활동**으로 격상되었습니다.
- **시스템 건강 유지:** AI의 분석력과 실행력을 활용해 리팩터링 과정을 가속화함으로써 시스템의 전반적인 건강을 유지하는 것이 현대적 방법론의 핵심입니다.

### 3. 개발자 역할의 진화 (Coder → Architect)

AI가 코드를 짜주는 시대에 개발자의 역할은 다음과 같이 변해야 합니다.

- **단순 구현자(Coder) 탈피:** 단순히 코드를 한 줄씩 타이핑하는 역할에서 벗어나야 합니다.
- **설계자 및 품질 관리자(Architect & Quality Manager):**
  - AI가 내놓은 결과물을 비판적으로 검증합니다.
  - 전체 시스템의 아키텍처 맥락에 맞는지 확인합니다.
  - 시스템의 장기적인 생존 가능성과 설계 품질에 대해 최종 책임을 집니다.

### 4. AI-Driven Refactoring의 흐름

- **수동적 보조에서 능동적 협업으로:** AI는 단순히 시키는 것만 하는 도구에서 벗어나, 코드 스멜을 선제적으로 감지하고 "Strategy 패턴을 적용하자" 혹은 "API를 Facade 패턴으로 단순화하자"와 같이 구체적인 개선안을 먼저 제안하는 **코파일럿(Co-pilot)** 역할을 수행합니다.

## AI-Driven Refactoring

### 1. AI 주도 리팩터링의 정의

AI 코딩 도구가 단순히 명령을 수행하는 '조수(Assistant)'에서 벗어나, 리팩터링 과정을 능동적으로 제안하고 이끄는 **'코파일럿(Co-pilot)'**으로 진화한 형태를 의미합니다.

- **능동적 분석:** AI가 코드를 미리 분석하여 잠재적인 **코드 스멜(Code Smell)**과 **안티 패턴(Anti-patterns)**을 식별합니다.
- **전략 제안:** 식별된 문제에 대해 "전략 패턴 적용", "파사드 패턴을 통한 API 단순화" 등 구체적인 설계 개선 방안을 여러 가지 제안합니다.
- **방법론적 의의:** AI의 분석력과 실행력을 활용하여 리팩터링의 전체 프로세스를 가속화하고 수준을 높이는 현대적 개발 방법론입니다.

### 2. AI 주도 리팩터링 워크플로우

리팩터링 과정은 인간 개발자와 AI 간의 협업으로 이루어지며, 총 5단계로 구성됩니다.

#### [1단계] 전략적 목표 설정 (인간)

개발자가 리팩터링의 목적(What & Why)을 정의합니다.

- **예시:** "결합도를 낮추고 새로운 결제 수단을 쉽게 추가할 수 있도록 결제 모듈의 설계를 개선하자."

#### [2단계] AI 기반 분석 및 옵션 생성 (AI)

AI가 대상 코드를 분석하고 설계 원칙 위반 사례를 찾아내어 여러 대안을 제시합니다.

- **내용:** 코드 스멜 파악, 디자인 원칙(SOLID) 위반 확인, 구체적인 코드 예시가 포함된 다수의 리팩터링 전략 제안.

#### [3단계] 비판적 의사결정 및 프롬프팅 (인간)

AI가 제안한 옵션들의 장단점을 평가하여 최적의 전략을 선택하고 실행 명령을 내립니다.

- **예시:** "제시된 옵션 중 2번 전략 패턴을 적용하는 방식으로 리팩터링을 진행해 줘."

#### [4단계] 자동화된 실행 및 테스트 생성 (AI)

선택된 전략에 따라 AI가 실제 코드 변환을 수행하고, 변경된 코드에 대한 유닛 테스트 초안을 작성합니다.

- **내용:** 코드 구조 재구성(Transformation), 해당 로직에 대한 드래프트 테스트 케이스 생성.

#### [5단계] 무결성 검증 및 최종 커밋 (인간)

TDD(테스트 주도 개발) 안전망을 통해 AI의 작업 결과물을 최종 확인합니다.

- **내용:** AI가 만든 테스트에 엣지 케이스(Edge Cases)를 보완하여 검증하고, 최종 코드를 검토(Review)한 후 시스템에 반영(Commit)합니다.

## AI 기반 리팩터링의 함정과 안티패턴

### 1. 과도한 신뢰로 인한 논리적 오류

- **위험성:** AI가 제시하는 제안을 비판 없이 수용할 경우, 겉보기에는 그럴듯하지만 특정 에지 케이스(Edge Case)에서 실패하는 미세한 버그가 유입될 수 있습니다.
- **대응:** AI의 출력물을 항상 객관적으로 검증하는 과정이 필수적입니다.

### 2. AI 유도형 안티패턴 (AI-induced Anti-patterns)

AI의 특성상 발생할 수 있는 설계상의 오류들입니다.

- **과잉 일반화 (Over-generalization):** 단순한 문제에 불필요하게 복잡한 디자인 패턴을 적용하여, 오히려 코드를 이해하기 어렵게 만드는 '오버 엔지니어링'을 초래할 수 있습니다.
- **맥락 맹목성 (Context-blindness):** 전체 시스템 아키텍처나 비즈니스 도메인에 대한 이해가 부족한 상태에서 특정 코드 블록만 최적화하려다 보니, 전체적인 조화를 깨뜨리는 국소적 최적화의 함정에 빠질 수 있습니다.

### 3. 개발자 역량 저하

- **무비판적 의존:** "생각 없는 리팩터링"을 위해 AI에만 지나치게 의존하게 되면, 왜 특정 설계가 더 우수한지에 대한 고민이 사라지게 됩니다. 이는 결과적으로 개발자 본인의 설계 능력을 퇴보시키는 원인이 됩니다.

### 4. 보안 우려 (Security Concerns)

- **데이터 유출:** 민감한 내부 코드를 외부 AI 서비스에 전송하기 전에는 반드시 조직의 보안 정책을 확인해야 합니다. 보안이 담보되지 않은 상태에서의 코드 공유는 심각한 자산 유출로 이어질 수 있습니다.

## TDD & AI: 리팩터링의 안전망

### 1. TDD의 새로운 역할

- AI가 주도하는 리팩터링의 **논리적 무결성을 검증**하는 최종 수단입니다.
- 예상치 못한 **회귀 버그(Regression)**를 방지하는 최후의 방어선 역할을 합니다.

### 2. 리팩터링 수행 프로세스 (4단계)

AI를 활용하여 안전하게 코드를 개선하는 구체적인 절차는 다음과 같습니다.

- **1단계: 기존 테스트 존재 여부 확인**
  - 대상 코드에 대한 테스트가 없다면 AI를 이용해 테스트 초안을 생성합니다.
  - 인간 개발자가 이를 검토하고 **경계 값(Edge Cases)** 등을 보완하여 테스트 세트를 완성합니다.
- **2단계: 테스트 통과 확인 (Red-Green 확인)**
  - 리팩터링 시작 전, 현재 모든 테스트가 통과하는지 반드시 확인합니다. 만약 실패한다면 버그부터 먼저 수정해야 합니다.
- **3단계: AI 리팩터링 수행**
  - AI에게 특정 리팩터링 전략을 제안하고 실행하도록 지시합니다.
- **4단계: 최종 검증 (Final Gate)**
  - 수정된 코드에 대해 **동일한 테스트 수트**를 다시 실행합니다.
  - **100% Pass**가 보장될 때만 AI의 결과물을 승인하고 반영합니다.

## 리팩터링 및 협업 워크플로우

리팩터링은 기존 기능에 영향을 주지 않아야 하므로, 안정성을 확보하기 위해 다음과 같은 엄격한 단계를 따릅니다.

1.  **전용 브랜치 생성 (Create a Branch)**
    - 작업의 단위를 명확히 분리하기 위해 `refactor/improve-payment-logic`과 같이 목적이 드러나는 별도의 리팩터링 브랜치를 생성합니다.

2.  **기존 테스트 실행 (Run Tests)**
    - 코드 수정 전, 현재 상태가 정상임을 확인하기 위해 `pytest` 등의 도구로 테스트를 수행합니다.
    - 모든 테스트가 통과하는 **Green** 상태임을 먼저 확인해야 합니다.

3.  **AI 기반 리팩터링 및 재검증 (AI-Driven Refactoring & Testing)**
    - AI에게 리팩터링 전략과 실행을 요청하여 코드를 개선합니다.
    - 수정 직후 다시 테스트를 실행하여 기능이 변하지 않았음을(Green 상태 유지) 즉시 확인합니다.

4.  **원자적 커밋 (Atomic Commit)**
    - "Refactor: Apply Strategy Pattern to payment logic"과 같이 변경 사항을 명확히 기술하여 원자적(추적 가능한 최소 단위)으로 커밋합니다.

5.  **풀 리퀘스트 생성 (Create a Pull Request)**
    - 단순한 코드 제출을 넘어, 리팩터링의 **'왜(Why)'**를 상세히 설명합니다.
    - AI가 제안했던 여러 옵션, 그중 특정 방식을 선택한 이유, 그리고 이를 검증한 과정을 동료들과 공유합니다.

## Strangler Fig Pattern

기존의 거대한 레거시 시스템을 한 번에 갈아엎는 대신, 나무 주위를 둘러싸며 자라 결국 기존 나무를 대체하는 '목 조르는 무화과나무(Strangler Fig)'처럼 **시스템을 점진적으로 교체**해 나가는 방식입니다. 이 패턴은 시스템 전체를 한꺼번에 새로 만드는 '빅뱅(Big Bang)' 방식의 위험을 피하기 위해 고안되었습니다.

### 핵심 프로세스 (4단계)

1.  **프록시/게이트웨이 도입:** 레거시 시스템 앞단에 요청을 가로챌 수 있는 프록시(Proxy)나 게이트웨이를 배치합니다.
2.  **신규 시스템 구현:** 새로운 기능이나 개선이 필요한 부분을 별도의 새로운 시스템(예: 마이크로서비스)으로 구현합니다.
3.  **요청 라우팅:** 게이트웨이 설정을 통해 해당 기능에 대한 요청만 기존 시스템이 아닌 신규 시스템으로 전달되도록 경로를 변경합니다.
4.  **점진적 반복 및 대체:** 이 과정을 반복하여 기능을 하나씩 옮기다 보면, 결국 레거시 시스템은 아무런 요청도 받지 않는 상태가 되어 자연스럽게 제거('strangled')됩니다.

### 이 패턴의 장점

- **리스크 감소:** 한꺼번에 시스템을 바꾸다 발생하는 대형 사고를 방지할 수 있습니다.
- **지속적 가치 전달:** 전체 교체가 끝날 때까지 기다릴 필요 없이, 완성된 기능부터 즉시 서비스에 적용할 수 있습니다.
- **안전한 후퇴 가능:** 신규 시스템에 문제가 생기면 게이트웨이 설정만 변경하여 즉시 기존 시스템으로 되돌릴 수 있습니다.

## 오픈소스와 리팩터링의 관계

### 1. 기여로서의 가치 (Value as a Contribution)

오픈소스 프로젝트에서 리팩터링은 단순한 코드 수정 이상의 의미를 가집니다.

- **동등한 가치:** 기존 코드의 가독성과 유지보수성을 향상시키는 PR은 새로운 기능을 추가하는 PR만큼이나 프로젝트에 중요하고 가치 있는 기여로 간주됩니다.
- **지속 가능성:** 코드의 구조를 개선함으로써 향후 다른 개발자들이 프로젝트를 이해하고 확장하는 데 도움을 줍니다.

### 2. 좋은 Pull Request의 특징 (Hallmarks of a Good PR)

성공적인 리팩터링 기여를 위해 갖추어야 할 핵심 요소들은 다음과 같습니다.

- **명확한 동기 (Clear Motivation):** "왜" 이 리팩터링이 필요한지, 어떤 이점을 주는지 논리적으로 설명해야 합니다.
- **작고 집중된 변경 (Small and Focused Changes):** 너무 방대한 양의 코드를 한꺼번에 수정하기보다, 특정 목적을 가진 최소 단위의 변경을 지향합니다.
- **테스트 통과 (100% Pass Rate):** 기존에 정의된 모든 테스트 케이스를 완벽하게 통과하여, 기능적 결함이 없음을 증명해야 합니다.
- **컨벤션 준수 (Adherence to Project Conventions):** 해당 프로젝트의 코딩 스타일, 명명 규칙, 아키텍처 가이드라인을 엄격히 따라야 합니다.

## 리팩터링 지침

### 1. 리팩터링 시간 배분 (The Boy Scout Rule)

- **질문**: "리팩터링에 얼마나 많은 시간을 투자해야 하나요?"
- **답변**: 특정 시간을 할당하기보다는 **"지속적(Continuous)"**으로 수행하는 것이 핵심입니다.
- **보이스카우트 규칙**: "코드를 체크아웃했을 때보다 더 깨끗한 상태로 체크인하라"는 원칙을 적용하여, 일상적인 개발 흐름 속에 리팩터링을 녹여내야 합니다.

### 2. 관리자와의 소통 및 설득

- **질문**: "관리자가 리팩터링할 시간을 주지 않습니다."
- **답변**: 리팩터링을 단순한 '코드 정리'가 아닌 **비즈니스 가치** 관점에서 프레임워크를 재설정하여 소통해야 합니다.
  - **버그 예방**: 결함 발생 가능성을 낮춤.
  - **개발 속도 향상**: 깨끗한 코드는 향후 기능 추가 및 수정 속도를 높임.
  - 즉, 기술적인 만족이 아니라 프로젝트의 장기적인 생산성과 직결됨을 강조해야 합니다.

### 3. 리팩터링의 중단 시점 (ROI 중심)

- **질문**: "언제 리팩터링을 멈춰야 할지 어떻게 알 수 있나요?"
- **답변**: 완벽주의(Perfectionism)를 경계해야 합니다.
  - **청결도**: 발견했을 때보다 조금이라도 더 깨끗해졌다면 충분한 진전으로 간주합니다.
  - **투자 대비 효과(ROI)**: 리팩터링 효과가 가장 높게 나타나는 부분에 우선순위를 두고 집중하며, 과도한 엔지니어링이 되지 않도록 적절한 지점에서 멈추는 절제가 필요합니다.

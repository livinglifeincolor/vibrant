## Major License Categories

오픈소스 라이선스는 크게 **허용적(Permissive) 라이선스**와 **카피레프트(Copyleft) 라이선스** 두 가지 범주로 나뉩니다. 이 둘의 핵심 차이는 '수정된 코드를 다시 공개해야 하는가'에 있습니다.

### 1. 허용적 라이선스 (Permissive Licenses)

가장 자유로운 형태의 라이선스입니다. 소프트웨어 사용, 수정, 배포에 대한 제약이 거의 없으며, 상용 소프트웨어 개발에 매우 친숙합니다.

- **주요 특징:**
  - 원본 제작자의 저작권 공지와 라이선스 문구만 유지하면 됩니다.
  - 수정된 코드를 오픈소스로 공개할 의무가 없습니다.
  - 가장 유명한 예시로는 **MIT, Apache 2.0, BSD**가 있습니다.
- **대표 사례:**
  - **MIT:** 매우 간결하며, 거의 모든 권한을 허용합니다. (예: React, Node.js, Vue.js)
  - **Apache 2.0:** MIT와 비슷하지만, 특허권 관련 조항이 명확하여 기업에서 선호합니다. (예: Android, Kubernetes, Spring)

### 2. 카피레프트 라이선스 (Copyleft Licenses)

오픈소스의 철학인 '공유'를 강제하는 라이선스입니다. 코드를 수정해서 배포할 때 동일한 라이선스를 적용해야 하므로 '전염성'이 있다고 표현하기도 합니다. ('Copyleft'는 저작권을 의미하는 'Copyright'와 반대되는 개념으로, 저작권을 기반으로 정보의 공유와 자유로운 재배포를 실천하는 권리 행사를 의미합니다.)

- **주요 특징:**
  - **Strong Copyleft (GPL 등):** 이 라이선스가 포함된 코드를 사용하여 파생 저작물을 만들면, 전체 소스 코드를 동일한 라이선스로 공개해야 합니다.
  - **Weak Copyleft (LGPL 등):** 라이브러리 형태로 링크하여 사용할 때는 전체 코드를 공개하지 않아도 되지만, 라이브러리 자체를 수정했다면 그 수정본은 공개해야 합니다.
- **대표 사례:**
  - **GPL (General Public License):** 가장 강력한 카피레프트입니다. 리눅스 커널(v2)과 Git 등이 이를 따릅니다.
  - **LGPL (Lesser GPL):** 독점 소프트웨어가 오픈소스 라이브러리를 사용할 수 있도록 허용 범위를 넓힌 형태입니다. (예: FFmpeg)

#### 라이선스 한눈에 비교하기

| 구분                 | 허용적 (MIT/Apache)    | 카피레프트 (GPL/LGPL)           |
| :------------------- | :--------------------- | :------------------------------ |
| **핵심 철학**        | 실용성과 자유로운 활용 | 오픈소스 생태계 유지와 환원     |
| **수정본 공개 의무** | 없음 (비공개 가능)     | 있음 (동일 라이선스 적용)       |
| **상용 서비스 활용** | 매우 쉬움              | 주의 필요 (코드 공개 범위 확인) |
| **제일 중요한 것**   | 저작권 공지 유지       | 소스 코드 공개 범위 준수        |

선택의 기준은 단순합니다. 내 코드가 널리 쓰이는 것이 목적이라면 **MIT**, 내 코드의 개선 사항이 반드시 세상에 다시 공유되길 바란다면 **GPL**을 선택하는 것이 논리적인 흐름입니다.

## 오픈소스 라이선스

### 1. 주요 라이선스별 상세 비교

라이선스는 크게 **의무 사항의 강도**에 따라 나눌 수 있습니다.

| 라이선스        | 카테고리        | 소스 코드 공개 의무 | 특징 및 용도                                                            |
| :-------------- | :-------------- | :------------------ | :---------------------------------------------------------------------- |
| **MIT**         | Permissive      | **없음**            | 가장 간결하고 제약이 적음. 누구나 자유롭게 사용 가능.                   |
| **BSD**         | Permissive      | **없음**            | MIT와 유사하나, 저작자의 이름을 홍보에 사용하지 못하게 하는 조항 포함.  |
| **Apache 2.0**  | Permissive      | **없음**            | 특허권 행사 방지 조항이 있어 기업 간 거래 및 대형 프로젝트에 적합.      |
| **LGPL**        | Weak Copyleft   | **부분적**          | 라이브러리로 링크 시에는 비공개 가능, 라이브러리 자체 수정 시에만 공개. |
| **GPL (v2/v3)** | Strong Copyleft | **필수**            | 해당 코드를 사용한 파생 저작물 전체를 반드시 오픈소스로 공개해야 함.    |

### 3. 상황별 라이선스 선택 가이드

1. **사용자가 가장 많아지길 원할 때:** **MIT** 또는 **BSD**를 선택하세요.
2. **기업들이 안심하고 사용하게 하고 싶을 때:** **Apache 2.0**이 정답입니다.
3. **내 코드를 가져간 사람이 개선한 결과물도 공유하길 원할 때:** **GPL**을 적용하세요.

## 버전 관리 시스템(VCS, Version Control System)

### 1. 버전 관리 시스템의 핵심 기능

- **이력 추적 (History Tracking):** 누가, 언제, 어떤 이유로 코드를 수정했는지 상세히 기록합니다.
- **롤백 (Rollback):** 특정 시점의 안정적인 상태로 코드를 되돌릴 수 있어 실수를 방지합니다.
- **협업 및 충돌 관리 (Collaboration):** 여러 사람이 동일한 파일을 수정할 때 발생하는 충돌을 감지하고 해결할 수 있도록 돕습니다.
- **비선형적 개발 (Branching):** 메인 코드에 영향을 주지 않고 새로운 기능을 개발하거나 버그를 수정하는 독립적인 작업 공간을 제공합니다.

### 2. 아키텍처에 따른 분류

#### 중앙집중형 (Centralized VCS)

모든 버전 관리 데이터가 하나의 중앙 서버에 저장되는 방식입니다. (예: SVN)

- **특징:** 구조가 단순하여 관리가 용이하고 보안 제어가 직관적입니다.
- **단점:** 서버에 장애가 발생하면 협업이 중단되는 **단일 장애점(SPOF)** 문제가 있으며, 네트워크 연결 없이는 버전 관리 작업을 수행할 수 없습니다.

#### 분산형 (Distributed VCS)

중앙 서버뿐만 아니라 모든 개발자의 로컬 PC에 전체 저장소와 이력이 복제되는 방식입니다. (예: Git)

- **특징:** \* **오프라인 작업:** 네트워크 없이도 커밋, 로그 확인, 롤백이 가능합니다.
  - **높은 성능:** 대부분의 연산이 로컬에서 이루어져 처리 속도가 매우 빠릅니다.
  - **안정성:** 모든 클론(Clone)이 완전한 백업 역할을 하므로 서버 복구가 용이합니다.

### 3. Git의 3가지 작업 영역

Git은 데이터를 관리할 때 세 가지 상태로 구분하여 흐름을 제어합니다.

1.  **Working Directory:** 실제로 파일을 수정하고 작업하는 로컬 공간입니다.
2.  **Staging Area (Index):** 커밋을 하기 전, 버전으로 기록할 변경 사항들을 선별하여 모아두는 준비 영역입니다.
3.  **Repository (Local/Remote):** 최종적으로 변경 사항이 기록되어 스냅샷으로 저장되는 공간입니다.

### 4. Git Workflow (표준 작업 흐름)

일반적인 버전 관리 프로세스는 다음과 같은 순서로 진행됩니다.

- **Initialize (`git init`):** 새로운 프로젝트에서 Git 저장소를 생성합니다.
- **Stage (`git add`):** 변경된 파일을 스테이징 영역으로 이동시킵니다.
- **Commit (`git commit`):** 스테이징 영역의 파일들을 메시지와 함께 로컬 저장소에 영구적으로 기록합니다.
- **Push (`git push`):** 로컬의 변경 사항을 GitHub와 같은 원격 저장소에 업로드합니다.
- **Pull (`git pull`):** 원격 저장소의 최신 변경 내용을 로컬로 가져와 동기화합니다.

VCS는 특히 오픈소스 프로젝트에서 라이선스 준수와 함께 개발자의 기술력을 증명하는 포트폴리오의 핵심적인 역할을 수행합니다.
